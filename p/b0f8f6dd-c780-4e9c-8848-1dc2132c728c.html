YAML

By the end of this guide you will be able to open any Kubernetes YAML file, find its four top-level parts, and explain what it will create. You will also write, apply, and inspect a small manifest yourself. This matters because long manifests stop looking scary once you know where to look.

Why this matters

A manifest is a YAML file that describes something you want Kubernetes to create. Every manifest, whether it makes a Namespace, a Pod or a Deployment, starts with the same four top-level parts: apiVersion, kind, metadata and spec.

When you meet a 200-line file, you do not read it line by line. You scan the left edge, find those four words, and treat everything indented underneath as belonging to the part above it. That one habit makes unfamiliar YAML readable.

Step 1: Write a manifest and spot the four parts

First, create a file called namespace.yaml. A Namespace is a named section of your cluster, and it is the simplest object to start with. We use it to see the four parts in their smallest form.

apiVersion: v1
kind: Namespace
metadata:
  name: demo

Save it, then print it back to check it:

cat namespace.yaml

Expected output

apiVersion: v1
kind: Namespace
metadata:
  name: demo

Notice there are only three parts here. Some kinds, like Namespace, can be created without a spec, and Kubernetes fills in the defaults. Most objects you will meet do have one, as you will see in Step 4.

Step 2: Read apiVersion and kind

apiVersion says which version of the Kubernetes API you are using to create the object. Many basic objects, such as Namespace, Pod and Service, simply use v1. Deployments use apps/v1, because they belong to the apps API group.

kind is the type of object you want. Change the kind and you change what gets created. You can ask your cluster which kinds it knows about and which version each uses:

kubectl api-resources | grep -E "^(namespaces|pods|deployments) "

Expected output

namespaces                        ns           v1                                     false        Namespace
pods                              po           v1                                     true         Pod
deployments                       deploy       apps/v1                                true         Deployment

Look at the version column. It tells you what to write in apiVersion, and the last column is the exact spelling for kind.

Step 3: Add metadata and apply it

metadata is the identity card of the object. It holds the name and, for namespaced objects, optionally a namespace. Kubernetes also gives every object its own unique ID, which you do not write yourself. Apply the manifest to create the namespace:

kubectl apply -f namespace.yaml

Expected output

namespace/demo created

Now look at what Kubernetes stored. You will see the name you chose, plus fields Kubernetes added, including the uid:

kubectl get namespace demo -o yaml

Expected output

apiVersion: v1
kind: Namespace
metadata:
  creationTimestamp: "2026-11-27T10:15:42Z"
  labels:
    kubernetes.io/metadata.name: demo
  name: demo
  resourceVersion: "5821"
  uid: 3f6c1a52-8d7e-4b0a-9c1e-2a7d5e4b9f10
spec:
  finalizers:
  - kubernetes
status:
  phase: Active

Your timestamp and uid will differ. Notice that Kubernetes added a spec and a status of its own. You wrote the desired state, and Kubernetes reports the current state.

Step 4: Write a spec for something that runs a container

spec is what you want, written as the desired state. Every kind has its own spec fields. For a Pod, the spec holds the list of containers and their image names. Create pod.yaml:

apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: demo
spec:
  containers:
  - name: web
    image: nginx:1.27

Apply it:

kubectl apply -f pod.yaml

Expected output

pod/web created

Check that it is running in the demo namespace:

kubectl get pods -n demo

Expected output

NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          12s

The first run may show ContainerCreating while the image downloads. Wait a few seconds and run it again.

Step 5: Use the left-edge scan on any file

Now practise the habit. Look at pod.yaml and read only the lines that start at the far left. You get apiVersion, kind, metadata and spec. Everything indented belongs to the part above it. You can do this with a quick command:

grep -E "^[a-zA-Z]" pod.yaml

Expected output

apiVersion: v1
kind: Pod
metadata:
spec:

Read it aloud: a version one Pod, with an identity, and a desired state. If you can say that, you can read the file.

Common mistakes

  • Wrong indentation. Symptom: an error like error converting YAML to JSON or a field that is silently ignored. Fix: use spaces, never tabs, and indent children consistently by two spaces under their parent.
  • Wrong apiVersion for the kind. Symptom: no matches for kind "Deployment" in version "v1". Fix: run kubectl api-resources and use the version shown for that kind, such as apps/v1.
  • Wrong capitalisation of kind. Symptom: no matches for kind "pod". Fix: write kinds exactly as shown, for example Pod, not pod.
  • Putting spec fields under metadata. Symptom: an unknown field error, or an object with no containers. Fix: check that spec: sits at the left edge, not indented under metadata:.
  • Applying into a namespace that does not exist. Symptom: namespaces "demo" not found. Fix: create the namespace first with kubectl apply -f namespace.yaml.

Quick recap

  1. Write a minimal manifest and find its top-level parts.
  2. Set apiVersion and kind, and check them with kubectl api-resources.
  3. Add metadata with a name, apply it, and see the uid Kubernetes adds.
  4. Write a spec with the desired state, such as the nginx:1.27 image.
  5. Scan the left edge to read any manifest quickly.
