OSS

By the end of this guide, you will be able to find real beginner-friendly Kubernetes ecosystem issues from your command line, set up a local workspace, and track your merged contributions. Open-source tools like Kubernetes are built on hundreds of small, incremental patches, and learning to ship a single small fix is the fastest way to build credibility as a DevOps engineer. You will use the official GitHub CLI (gh) and standard Git workflows to turn passive reading into merged code.

Why this matters

Most beginners fail to contribute to Kubernetes projects because they pick massive architecture issues or wait until they feel like an expert. Kubernetes and its ecosystem (Helm, Prometheus, Envoy) use issue labels like good first issue and help wanted specifically to welcome newcomers. Knowing how to query these tasks directly from your terminal eliminates analysis paralysis and gets you straight into the codebase.

Step 1: Install and authenticate the GitHub CLI

Install the official GitHub CLI tool (gh) and log in so you can search repositories and manage pull requests directly from your terminal. This avoids context switching between your browser and editor.

gh auth status

Expected output

github.com
  ✓ Logged in to github.com account yourname (keyring)
  - Active account: true
  - Git operations protocol: https
  - Token: gho_************************************
  - Token scopes: 'gist', 'read:org', 'repo'

Step 2: Search for beginner issues across Kubernetes repositories

Use the gh issue list command to filter for open issues labeled good first issue in an active ecosystem project like Kubernetes SIGs examples or documentation. This shows you well-scoped tasks such as typo fixes, documentation updates, or small unit tests.

gh issue list --repo kubernetes-sigs/kind --label "good first issue" --state open --limit 5

Expected output

#3412  Update node image documentation for v1.31      good first issue  about 2 days ago
#3398  Clarify docker socket permission error         good first issue  about 1 week ago
#3345  Fix typo in quick-start guide                  good first issue  about 3 weeks ago

Step 3: Fork and clone the target repository

Once you identify an issue you want to resolve, fork the repository to your personal profile and clone it locally using gh repo fork. This command configures both your personal fork (origin) and the upstream project repository (upstream) automatically.

gh repo fork kubernetes-sigs/kind --clone=true

Expected output

✓ Created fork yourname/kind
✓ Cloned fork
✓ Added remote upstream

Step 4: Create a dedicated branch and inspect the changes

Change into the repository directory and cut a new branch for your specific fix. Keeping your change isolated on a distinct feature branch ensures clean Git history and avoids conflicts with main.

cd kind && git checkout -b fix-docs-typo

Expected output

Switched to a new branch 'fix-docs-typo'

Step 5: Check your merged contributions

After you submit your pull request and address code review feedback, the project maintainers merge your code. Run this search query with the GitHub CLI to view only your merged pull requests across GitHub, proving your contributions are complete.

gh search prs --author "@me" --state merged --limit 5

Expected output

#3345  Fix typo in quick-start guide  kubernetes-sigs/kind  MERGED  about 1 hour ago

Common mistakes

  • Taking on an unassigned issue without commenting: Other contributors might already be working on it. Check the comments first and post a quick note asking the maintainers if the issue is still open for a PR.
  • Submitting a pull request directly from your main branch: If upstream merges new commits while your PR is in review, syncing main becomes messy. Always create a dedicated branch like git checkout -b fix-issue-123.
  • Ignoring sign-off requirements: Most CNCF and Kubernetes projects require the Developer Certificate of Origin (Signed-off-by). If your commits fail CI checks, ensure you commit with git commit -s to attach your signature.
  • Submitting huge PRs covering multiple problems: Reviewers will delay reviewing massive changes. Keep your PR focused on exactly one issue or bug.

Quick recap

  1. Authenticate your terminal with gh auth status to interact with GitHub repositories directly.
  2. Filter target repositories for tasks marked with the good first issue label.
  3. Fork and clone the repository with gh repo fork to configure remotes automatically.
  4. Create an isolated feature branch using git checkout -b before making your edits.
  5. Track and verify your completed work using gh search prs --author "@me" --state merged.
