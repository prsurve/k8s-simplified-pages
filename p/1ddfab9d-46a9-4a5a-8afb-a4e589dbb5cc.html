EXPLAIN

Staring at a blank YAML file and guessing whether a field is called envVars, environment, or env wastes hours. By the end of this guide, you will be able to query the exact structure, data type, and requirements of any Kubernetes object directly from your terminal. You will never need to open a web browser to check API documentation again.

Why this matters

The Kubernetes API contains thousands of fields across dozens of resources. Field names are strict, case-sensitive, and change depending on which API version you target. Browsing online documentation often pulls up documentation for the wrong version of Kubernetes. kubectl explain reads OpenAPI schemas directly from the cluster you are currently connected to, giving you accurate, version-matched documentation instantly.

Step 1: Inspect a top-level resource

Run kubectl explain on a resource name to see its group, version, description, and top-level fields. This confirms how the resource is identified in the cluster and lists its primary sections.

kubectl explain pod

Expected output

KIND:       Pod
VERSION:    v1

DESCRIPTION:
    Pod is a collection of containers that can run on a host. This resource is
    created by clients and scheduled onto hosts.

FIELDS:
    apiVersion	<string>
        APIVersion defines the versioned schema of this representation of an
        object.

    kind	<string>
        Kind is a string value representing the REST resource this object
        represents.

    metadata	<Object>
        Standard object's metadata.

    spec	<PodSpec>
        Specification of the desired behavior of the pod.

    status	<PodStatus>
        Most recently observed status of the pod.

Step 2: Drill into nested fields using dot notation

Navigate down into nested fields by separating field names with a period (.). Drilling into pod.spec reveals the exact configuration options available when defining a Pod's operational workload.

kubectl explain pod.spec

Expected output

KIND:       Pod
VERSION:    v1

RESOURCE:   spec <PodSpec>

DESCRIPTION:
    Specification of the desired behavior of the pod. More info:
    https://git.k8s.io/community/contributors/devel/sig-architecture/api-conventions.md#spec-and-status

FIELDS:
    activeDeadlineSeconds	<integer>
        Optional duration in seconds the pod may be active on the node.

    affinity	<Affinity>
        If specified, the pod's scheduling constraints.

    containers	<[]Container> -required-
        List of containers belonging to the pod. Containers cannot currently be
        added or removed. There must be at least one container in a Pod. Cannot
        be updated.

    dnsPolicy	<string>
        Set DNS policy for the pod. Defaults to "ClusterFirst".

    restartPolicy	<string>
        Restart policy for all containers within the pod. One of Always,
        OnFailure, Never. Default to Always.

Step 3: Check types and required fields

Drill further down to determine how to format values and spot mandatory settings. Looking at pod.spec.containers shows that containers requires a list (denoted by []Container), and inspecting inside shows which keys are marked as -required-.

kubectl explain pod.spec.containers.image

Expected output

KIND:       Pod
VERSION:    v1

FIELD:      image <string>

DESCRIPTION:
    Container image name. More info:
    https://kubernetes.io/docs/concepts/containers/images This field is
    optional to allow higher level config management to default or override
    container images in workload controllers like Deployments and StatefulSets.

Step 4: Expand the full tree with recursive view

When you need an architectural overview of all available keys under a specific section without reading long descriptions, use the --recursive flag. Grep or scroll through the tree to locate unknown keys quickly.

kubectl explain pod.spec.containers.resources --recursive

Expected output

KIND:       Pod
VERSION:    v1

RESOURCE:   resources <ResourceRequirements>

DESCRIPTION:
    Compute Resources required by this container. Cannot be updated. More info:
    https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/

FIELDS:
    claims	<[]ResourceClaim>
       name	<string>
       request	<string>
    limits	<map[string]Quantity>
    requests	<map[string]Quantity>

Step 5: Verify fields for different API versions

Some resources exist in multiple API versions, such as HorizontalPodAutoscaler or Ingress. Pass the --api-version flag to inspect fields for an older or newer version without leaving your terminal.

kubectl explain deployment --api-version=apps/v1

Expected output

KIND:       Deployment
VERSION:    apps/v1

DESCRIPTION:
    Deployment enables declarative updates for Pods and ReplicaSets.

FIELDS:
    apiVersion	<string>
    kind	<string>
    metadata	<Object>
    spec	<DeploymentSpec>
    status	<DeploymentStatus>

Common mistakes

  • Typo in the field name: Running kubectl explain pod.spec.container prints an error saying the field does not exist. Remember that containers is plural; use kubectl explain pod.spec first to check the correct spelling.
  • Missing capitalisation context: Querying kubectl explain Pod.Spec works, but searching subfields like pod.spec.RestartPolicy fails. Root kinds can be capitalized, but internal field names are strictly camelCase in Kubernetes schemas.
  • Forgetting that brackets mean a list: Seeing <[]Container> means the YAML requires a hyphenated list syntax (- name: ...), not a plain key-value map. Failing to add the list dash causes YAML schema validation errors during kubectl apply.
  • Reading outdated local cached schemas: If you recently upgraded your cluster control plane, kubectl explain might still reflect cached discovery docs. Clear the local cache directory at ~/.kube/cache to refresh the schemas.

Quick recap

  1. Run kubectl explain <resource> to inspect the base definition and identify high-level blocks like spec or metadata.
  2. Use dot syntax like kubectl explain pod.spec to move down the configuration tree.
  3. Check field signatures to confirm data types (<string>, <integer>, <map>) and identify -required- fields.
  4. Add --recursive to sub-paths to print a structural tree of available keys without description text.
  5. Pass --api-version to examine resources when migrating between deprecated and current API schemas.
