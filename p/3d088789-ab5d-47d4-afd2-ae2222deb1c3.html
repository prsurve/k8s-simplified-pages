Your logs have 50,000 slow queries. You still don't know which one is breaking prod. That's the problem with logging slow queries instead of tracing them. A log line tells you a query took 4 seconds — it doesn't tell you which service, which endpoint, or which user hit it. OpenTelemetry traces attach that slow query to a span with full context, and span durations turn into reliability metrics like P99 latency you can actually alert on. TRACE

Here's the quick OTel setup to turn slow queries into actionable metrics: 1) Instrument your app with an OpenTelemetry SDK (most languages have one — Node, Java, Python, Go) so every incoming request creates a trace with a unique ID. 2) Wrap your DB calls in spans — most ORMs and DB drivers have OTel auto-instrumentation, so a slow query shows up as a child span with exact duration, query text, and the parent request's service/endpoint attached. 3) Run the OpenTelemetry Collector (deploy it as a sidecar or a Deployment in your cluster) to receive these traces via OTLP, then export them two ways: to a tracing backend like Jaeger or Tempo for the waterfall view, and to Prometheus as a histogram metric (http_server_duration_seconds or db_query_duration_seconds) via the collector's Prometheus exporter. 4) In Prometheus/Grafana, run histogram_quantile(0.99, rate(db_query_duration_seconds_bucket[5m])) grouped by endpoint to get real P99 latency per API route instead of a flat 'average query time' number. 5) Set your alert on that P99 metric crossing a threshold (say, checkout API P99 > 2s for 5 minutes) instead of alerting on log line volume. Result: when it fires, you already know the exact endpoint, service, and query — no more grepping logs at 2am trying to correlate a timestamp to a customer complaint.
