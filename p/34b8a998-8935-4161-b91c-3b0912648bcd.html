Here's the lazy debugging flow I use every single time something breaks in Kubernetes, in order: 1) kubectl get pods — check STATUS and RESTARTS first, this alone tells you if it's a crash, a pending/scheduling issue, or an image pull problem. 2) kubectl describe pod <name> — scroll straight to the Events section at the bottom, this is where Kubernetes literally narrates what happened (failed mounts, OOMKilled, image pull errors, probe failures). 3) kubectl logs <pod> -f to tail live logs, or kubectl logs <pod> --previous if the container already crashed and restarted (this is the one beginners forget — without --previous you're reading the NEW container's empty logs, not the one that died). 4) kubectl exec -it <pod> -- sh (or bash if available) to get an actual shell inside the running container and poke at env vars, files, and network from inside. 5) kubectl port-forward pod/<name> 8080:80 to hit the service directly in your browser or with curl, without needing a full ingress or load balancer set up. Run these five in order before you touch the application code — most 'mystery' bugs are actually just a misread env var, a missing config map, or a probe timing out, and this flow surfaces that in under two minutes.
