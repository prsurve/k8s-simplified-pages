PENDING

By the end of this guide you will be able to take any pod stuck in Pending, find the exact reason the scheduler gave, and fix it without restarting anything at random. We will reproduce a real stuck pod, read its Events, and fix it.

This matters because Pending is not an error. It means the scheduler has not placed your pod on a node yet, and it records exactly why. Reading that one line saves you from the 40-minute restart spiral.

Why this matters

When you run kubectl get pods, the STATUS column tells you what is happening, but never why. Deleting pods, restarting deployments and bouncing nodes changes nothing, because the cause is almost always a scheduling constraint: not enough CPU or memory, a volume that is not bound, or a node taint. The scheduler writes that reason into the pod's Events. Your job is to read it.

Step 1: Create a pod that cannot be scheduled

First we make the problem on purpose. This deployment called web asks for far more CPU than a small cluster has, so the scheduler cannot place it. Save it as web.yaml and apply it in the demo namespace.

kubectl create namespace demo
cat <<'EOF' > web.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
spec:
  replicas: 1
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        resources:
          requests:
            cpu: "64"
EOF
kubectl apply -f web.yaml

Expected output

namespace/demo created
deployment.apps/web created

Step 2: See the status, and notice what it does not say

List the pods. This is where most people get stuck, because the output shows the state but gives no reason.

kubectl get pods -n demo

Expected output

NAME                   READY   STATUS    RESTARTS   AGE
web-6d8f7c9b5d-x2k4q   0/1     Pending   0          2m

Pending with zero restarts means the container never started. Nothing crashed. The pod is waiting to be placed on a node.

Step 3: Describe the pod and scroll to the bottom

Run kubectl describe pod on the pod name from Step 2. It prints a long wall of text. Ignore almost all of it and go straight to the last section, Events. Your pod name will differ, so replace web-6d8f7c9b5d-x2k4q with the name you saw.

kubectl describe pod web-6d8f7c9b5d-x2k4q -n demo

Expected output

...
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  2m    default-scheduler  0/3 nodes are available: 3 Insufficient cpu. preemption: 0/3 nodes are available: 3 No preemption victims found for incoming pod.

This is the scheduler talking. It checked all three nodes and each one said no because of CPU. That is your whole answer in one line.

Step 4: Fix the cause the event named

The event said CPU, so we lower the request to something reasonable. Use kubectl set resources to change it on the deployment. A new pod is created and the old one is replaced.

kubectl set resources deployment web -n demo --requests=cpu=100m
kubectl get pods -n demo

Expected output

deployment.apps/web resource requests updated
NAME                   READY   STATUS    RESTARTS   AGE
web-7c5b9d6f84-m8wzp   1/1     Running   0          12s

Step 5: Learn to read other Pending reasons

The Events message changes with the cause, and the cause tells you where to look. Here is a pod blocked by storage. Nothing is wrong with CPU, the claim was never bound.

kubectl get events -n demo --field-selector reason=FailedScheduling

Expected output

LAST SEEN   TYPE      REASON             OBJECT          MESSAGE
8s          Warning   FailedScheduling   pod/web-data    0/3 nodes are available: pod has unbound immediate PersistentVolumeClaims. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

Common messages and what they mean:

  • Insufficient cpu or Insufficient memory: requests are larger than any node can offer.
  • unbound immediate PersistentVolumeClaims: check kubectl get pvc -n demo.
  • node(s) had untolerated taint: the pod needs a matching toleration or a different node.
  • didn't match Pod's node affinity/selector: your nodeSelector or affinity matches no node.

Common mistakes

  • Restarting or deleting the pod first. Symptom: it comes back as Pending with the same age reset. Fix: run kubectl describe pod and read Events before touching anything.
  • Reading the top of the describe output. Symptom: pages of fields and no answer. Fix: scroll to the bottom, the Events section holds the reason.
  • Looking at logs. Symptom: kubectl logs returns nothing or an error. Fix: a Pending pod has no container yet, so there are no logs. Use Events.
  • Describing the deployment instead of the pod. Symptom: no FailedScheduling message. Fix: describe the pod itself, the scheduler writes events against it.
  • Forgetting the namespace. Symptom: NotFound errors. Fix: add -n demo to every command.

Quick recap

  1. Create the web deployment whose pod cannot be scheduled.
  2. Run kubectl get pods -n demo and see Pending without a reason.
  3. Run kubectl describe pod and read the Events section at the bottom.
  4. Fix exactly what the event names, here CPU requests.
  5. Use the message to recognise other causes: storage, taints and selectors.

Describe first, guess never.
