Shortly, you'll be able to tell whether the kubelet on your node runs as root, confirm what that means at the kernel level, and set up a staging node to test rootless mode. This matters because the kubelet starts and controls every pod on the machine, so its user decides how far a container escape can reach.

Step 1: Find out which user runs the kubelet

The kubelet is the agent on every node. It starts your pods, watches their health, and reports to the control plane. Start by listing the process and its owner. Run this on any node in your cluster, and use a staging node if you can.

Why: the owner shown here is the user that holds the keys to the machine, so this is your baseline.

ps -o user,pid,cmd -C kubelet

Expected output

USER     PID CMD
root    1423 /usr/bin/kubelet --config=/var/lib/kubelet/config.yaml --kubeconfig=/etc/kubernetes/kubelet.conf

If the first column says root, your kubelet has full host power. Most clusters look like this today.

Step 2: Confirm the real user IDs from the kernel's view

Process listings can be misleading, so check the kernel's record. The Uid line in /proc shows the real, effective, saved, and filesystem user IDs, and the uid_map file shows how user IDs inside a user namespace map to the host.

Why: a process inside a user namespace can think it is root while being an ordinary user on the host. This check shows which situation you are in.

PID=$(pgrep -o -x kubelet)
grep '^Uid' /proc/$PID/status
cat /proc/$PID/uid_map

Expected output

Uid:    0       0       0       0
         0          0 4294967295

Here, 0 maps to host user 0, and the range covers all IDs. That means the kubelet is real root on the host. A rootless kubelet would show a mapping such as 0 1000 1, meaning the process believes it is root, but it is host user 1000.

Step 3: Check whether the feature gate is set on your staging node

KubeletInUserNamespace is a feature gate, which is a switch the kubelet reads at startup. Check your kubelet configuration file and the process arguments for it. Run this on the staging node only.

Why: you need to know whether the gate is already on, off, or not mentioned at all before you change anything.

sudo grep -A3 featureGates /var/lib/kubelet/config.yaml
ps -o cmd -C kubelet | grep -o 'feature-gates=[^ ]*'

Expected output

(no output)

No output means the gate is not set, so the kubelet uses its default. Check the Kubernetes release notes for your version to confirm the feature's current stage, because the stage determines whether you can enable it safely. Beta means it is available but opt-in, so you must enable it yourself.

Step 4: Enable the gate and restart the kubelet on staging

Add the gate to the kubelet configuration file. Setting it through the config file is cleaner than editing command-line flags, and it survives restarts. This change alone does not make the kubelet rootless. Rootless mode also needs the kubelet started inside a user namespace, usually through a wrapper such as RootlessKit, and that setup varies by distribution and container runtime. Follow the official rootless documentation for the wrapper and unit file.

Why: the feature gate tells the kubelet it is allowed to run in a user namespace. Without it, the kubelet will refuse that setup.

apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
featureGates:
  KubeletInUserNamespace: true

Then restart the service and confirm it is healthy.

sudo systemctl restart kubelet
systemctl status kubelet --no-pager

Expected output

● kubelet.service - kubelet: The Kubernetes Node Agent
     Loaded: loaded (/usr/lib/systemd/system/kubelet.service; enabled)
     Active: active (running) since Tue 2025-06-03 10:14:22 UTC; 4s ago

If the status is failed, read the logs with journalctl -u kubelet --no-pager -n 50 before doing anything else.

Step 5: Prove pods still run on the test node

Deploy a small workload into a namespace called demo, then confirm the node is ready and the pod runs. This tells you whether the trade-offs you accepted are workable.

Why: rootless mode can change how some features behave, so a real pod is the only reliable test.

apiVersion: v1
kind: Namespace
metadata:
  name: demo
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
spec:
  replicas: 1
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: nginx:1.27
        ports:
        - containerPort: 80

Apply it and check the result.

kubectl apply -f web.yaml
kubectl -n demo get pods -o wide

Expected output

namespace/demo created
deployment.apps/web created
NAME                   READY   STATUS    RESTARTS   AGE   IP           NODE
web-7d9f6b8c5-x2k4p    1/1     Running   0          21s   10.244.1.6   staging-node-1

If the pod sits in Pending or ContainerCreating, describe it with kubectl -n demo describe pod and check the events.

Why this matters

If the kubelet runs as root and a container escapes, the attacker lands on the host with root. That means they can read secrets from other pods, change system files, and move to other machines. With rootless mode, the same escape reaches a user with no real power over the machine, so the damage stays much smaller.

Be honest about the trade-off. The feature is beta, it needs setup, and some features behave differently. Test it on a staging node before you touch production.

Common mistakes

  • Checking the wrong process. You run ps and see a kubelet line from a container or an old shell, and you think the node is safe. Fix it by using pgrep -o -x kubelet, which matches only the exact process name and returns the oldest one.
  • Enabling the gate on a live node. Your pods restart unexpectedly after you change the config. Fix it by doing every change on a staging node first and draining production nodes before any change.
  • Assuming the gate alone is rootless. You set KubeletInUserNamespace and the kubelet still shows Uid: 0 0 0 0. Fix it by checking uid_map in Step 2 and confirming the kubelet starts inside a user namespace through the wrapper described in the rootless docs.
  • Ignoring the feature stage. You enable an alpha or unclear feature in production because a post said it was ready. Fix it by reading the release notes for your exact version before enabling any gate.

Quick recap

  1. Run ps -o user,pid,cmd -C kubelet to see who owns the kubelet process.
  2. Check /proc/<pid>/status and uid_map to confirm real root versus a mapped user.
  3. Look for existing feature gates in the kubelet config file and process arguments.
  4. Enable KubeletInUserNamespace in the kubelet configuration on a staging node, then restart the kubelet.
  5. Deploy a test workload in the demo namespace and confirm the pod runs before you consider anything else.
