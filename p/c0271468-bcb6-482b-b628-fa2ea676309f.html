ROADMAP

In this guide, you will learn how to translate three distinct DevOps career paths into real Kubernetes tasks you can practice today. Instead of getting overwhelmed by buzzwords, you will build the foundational workloads that Platform Engineers, SREs, and DevSecOps Engineers configure on the job every week. Mastering these core patterns gives you a targeted portfolio that stands out in job applications.

Step 1: Create an isolated namespace for platform workloads

A Platform Engineer focuses on internal developer platforms, which starts with multi-tenant workspace separation. You will create a dedicated namespace called demo where all your application resources live safely away from default cluster internals.

kubectl create namespace demo

Expected output

namespace/demo created

Step 2: Deploy an application baseline as a DevOps Engineer

A traditional DevOps or Cloud Engineer bridges development and operations by running containerized services predictably. You will deploy a standard NGINX workload named web using the official nginx:1.27 image inside the demo namespace.

kubectl create deployment web --image=nginx:1.27 -n demo --replicas=2

Expected output

deployment.apps/web created

Step 3: Implement SRE health checks and resource limits

Site Reliability Engineers care about system stability, automated recovery, and resource boundaries. You will patch the web deployment with a liveness probe and resource limits so Kubernetes knows when to restart a crashed process and prevents the container from starving the node.

kubectl apply -n demo -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - containerPort: 80
        resources:
          limits:
            memory: "128Mi"
            cpu: "250m"
          requests:
            memory: "64Mi"
            cpu: "100m"
        livenessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 10
EOF

Expected output

deployment.apps/web configured

Step 4: Enforce security context as a DevSecOps Engineer

DevSecOps Engineers secure application delivery by enforcing least-privilege standards before code ever hits production. You will update the deployment to run as a non-root user and disallow privilege escalation, blocking attackers if the container is compromised.

kubectl apply -n demo -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 101
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - containerPort: 80
        securityContext:
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: false
        resources:
          limits:
            memory: "128Mi"
            cpu: "250m"
          requests:
            memory: "64Mi"
            cpu: "100m"
EOF

Expected output

deployment.apps/web configured

Step 5: Verify the rollout across role criteria

A Release or CI/CD Engineer ensures that all configuration updates roll out cleanly without downtime. You will inspect the deployment rollout status to confirm both pods are running the updated configuration smoothly.

kubectl rollout status deployment/web -n demo

Expected output

deployment "web" successfully rolled out

Why this matters

Job descriptions list dozens of technologies, but engineering hiring managers look for role-specific discipline. A generalist often writes fragile deployments with no resource caps or security parameters. By practicing explicit configurations—like setting resource boundaries for SRE roles or hardening container permissions for DevSecOps—you prove you can execute the actual responsibilities of the role you applied for.

Common mistakes

  • Missing namespace context: The reader runs commands without -n demo, causing resources to deploy into default. Symptom: kubectl get pods shows nothing or reports NotFound. Fix: Always specify the namespace flag -n demo or set your namespace context using kubectl config set-context --current --namespace=demo.
  • Running non-root on default NGINX: The reader sets runAsUser to an arbitrary ID on standard images that bind to port 80 or write to protected directories. Symptom: Pod status reports CrashLoopBackOff with permission denied errors. Fix: Use unprivileged images (like nginxinc/nginx-unprivileged) or configure appropriate user IDs and volume mounts for logging directories.
  • Aggressive probe settings: The reader sets initialDelaySeconds to zero or periodSeconds too low for a slow-starting app. Symptom: The pod repeatedly restarts before finishing initialization. Fix: Set reasonable warmup times using initialDelaySeconds or implement a dedicated startupProbe.

Quick recap

  1. Created a dedicated demo namespace to establish multi-tenant platform isolation.
  2. Deployed an initial two-replica web workload using the official nginx:1.27 image.
  3. Added CPU/memory limits and an HTTP liveness probe to align with SRE reliability practices.
  4. Hardened container execution permissions using pod-level security contexts for DevSecOps alignment.
  5. Inspected the active deployment status to confirm automated rollout completion.
