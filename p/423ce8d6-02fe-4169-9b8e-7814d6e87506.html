I once thought a Kubernetes cluster was one big computer. I lost an afternoon to that idea. A cluster is two jobs split across machines: a control plane that makes decisions, and worker nodes that run your Pods. Think of a restaurant: the manager picks the kitchen, the kitchens do the cooking. Once you see the split, the rest of Kubernetes stops feeling random. What did you first assume a cluster was? PART3

Once you finish this guide, you will be able to look at any cluster and say which machines make decisions and which ones run your code. That split explains most of what Kubernetes does, and it is the first thing that stops the system from feeling random.

Step 1: Confirm which machines are in your cluster

Start by listing the nodes. Each node is a physical computer or a virtual machine that Kubernetes can use. Some of them carry the control plane, and the rest are workers.

kubectl get nodes

Expected output

NAME            STATUS   ROLES           AGE   VERSION
control-plane   Ready    control-plane   12d   v1.30.2
worker-1        Ready    <none>          12d   v1.30.2
worker-2        Ready    <none>          12d   v1.30.2

The ROLES column shows which node carries the control plane. The workers have no role label because their only job is running Pods.

Step 2: Look at the control plane components

Next, list the system Pods in the kube-system namespace. These are the control plane components, plus a few helpers, running as Pods on the cluster. On managed clusters some of these are hidden from you, but on a kubeadm-style cluster you can see them directly.

kubectl get pods -n kube-system

Expected output

NAME                                    READY   STATUS    RESTARTS   AGE
coredns-7db6d8ff9d-k2mqz                1/1     Running   0          12d
etcd-control-plane                      1/1     Running   0          12d
kube-apiserver-control-plane            1/1     Running   0          12d
kube-controller-manager-control-plane   1/1     Running   0          12d
kube-proxy-8hz4t                        1/1     Running   0          12d
kube-proxy-lr5vn                        1/1     Running   0          12d
kube-scheduler-control-plane            1/1     Running   0          12d

The key ones are etcd, which holds the cluster's records, kube-apiserver, which is the front door every command passes through, kube-scheduler, which picks a node for each Pod, and kube-controller-manager, which keeps the number of Pods matching what you asked for. Notice that kube-proxy appears once per node, which hints that some components live on every machine.

Step 3: Ask for three copies of your app

Create a namespace called demo, then create a Deployment called web with three replicas. A Deployment is the object you use to say "keep this app running this many times."

kubectl create namespace demo
kubectl -n demo create deployment web --image=nginx:1.27 --replicas=3

Expected output

namespace/demo created
deployment.apps/web created

You sent this request to the API server, and it was recorded in etcd. At this point, no container has started yet. The control plane has only written down what you want.

Step 4: See where each copy was placed

Now list the Pods with -o wide, which adds a column showing the node each Pod was assigned to. This is the decision the scheduler made.

kubectl -n demo get pods -o wide

Expected output

NAME                  READY   STATUS    RESTARTS   AGE   IP            NODE       NOMINATED NODE
web-6f9c7d8b5-4xk2p   1/1     Running   0          20s   10.244.1.4    worker-1   <none>
web-6f9c7d8b5-9qwlr   1/1     Running   0          20s   10.244.2.7    worker-2   <none>
web-6f9c7d8b5-tn8zv   1/1     Running   0          20s   10.244.1.5    worker-1   <none>

The NODE column shows the split you were missing. The scheduler chose the nodes, and the workers ran the Pods. None of these Pods are running on control-plane.

Step 5: Trace the decision in the event log

Finally, read the events in the namespace to see the handoff: the scheduler decided, and then a worker's kubelet started the container.

kubectl -n demo get events --sort-by=.lastTimestamp

Expected output

LAST SEEN   TYPE     REASON              OBJECT                     MESSAGE
30s         Normal   Scheduled           pod/web-6f9c7d8b5-4xk2p    Successfully assigned demo/web-6f9c7d8b5-4xk2p to worker-1
29s         Normal   Pulled              pod/web-6f9c7d8b5-4xk2p    Container image "nginx:1.27" already present on machine
28s         Normal   Started             pod/web-6f9c7d8b5-4xk2p    Started container web

The Scheduled event comes from the control plane. The Pulled and Started events come from the worker node. Those two lines are the restaurant example in real output: the manager picks the kitchen, and the kitchen does the cooking.

Why this matters

When something breaks, the split tells you where to look. If a Pod never gets a node, the problem is in the control plane, usually the scheduler or a missing resource. If a Pod has a node but will not start, the problem is on that worker, such as an image that cannot be pulled. Knowing which side owns the failure saves you from guessing across the whole cluster.

Common mistakes

  • Mistake: Treating the cluster as one big machine and expecting kubectl to run containers directly. Symptom: You check your own laptop or the control plane node and find no nginx process. Fix: Run kubectl -n demo get pods -o wide and look at the NODE column, then inspect that worker.
  • Mistake: Running application workloads on the control plane node because it is the only one you know. Symptom: The node gets slow, and the cluster's own components start competing with your app for CPU and memory. Fix: Keep your Pods on worker nodes, and check kubectl get nodes to confirm which nodes carry the control-plane role.
  • Mistake: Assuming a successful create command means the app is running. Symptom: You see deployment.apps/web created but the site does not respond. Fix: Check kubectl -n demo get pods for Running status, then read kubectl -n demo get events for the reason if it is not running.

Quick recap

  1. List nodes with kubectl get nodes to see the control plane and workers.
  2. List kube-system Pods to find the control plane components.
  3. Create the demo namespace and the web Deployment with three replicas.
  4. Check the NODE column with kubectl -n demo get pods -o wide to see where each copy runs.
  5. Read the events to confirm the scheduler decided and a worker ran each Pod.
