ROADMAP

By the end of this guide, you will deploy a working web application using the five core Kubernetes objects: Pods, Deployments, Services, ConfigMaps, and Secrets. You will see firsthand how these resources wire together and heal automatically when things break. This practical foundation will save you weeks of memorizing API documentation you do not need yet.

Step 1: Create the namespace and store your configuration

Before running your container, separate its environment settings and credentials from the image using a ConfigMap and a Secret. We create an isolated namespace called demo, an unencrypted ConfigMap for plain configuration strings, and a Secret for sensitive credentials like API tokens.

kubectl create namespace demo
kubectl create configmap web-config --from-literal=APP_ENV=production -n demo
kubectl create secret generic web-secret --from-literal=DB_PASSWORD=supersecret -n demo

Expected output

namespace/demo created
configmap/web-config created
secret/web-secret created

Step 2: Deploy the self-healing application

A Pod runs your container, but you should rarely create a standalone Pod directly because it cannot recover if it crashes or the node dies. Instead, you create a Deployment, which defines the desired state, mounts the ConfigMap and Secret into the container environment, and continuously keeps the specified number of Pod replicas alive.

kubectl apply -n demo -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - containerPort: 80
        env:
        - name: APP_ENV
          valueFrom:
            configMapKeyRef:
              name: web-config
              key: APP_ENV
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: web-secret
              key: DB_PASSWORD
EOF

Expected output

deployment.apps/web created

Step 3: Verify the Pods and read the injected configuration

Check that the Deployment scheduled and started your two Pods successfully. Then, execute an environment check inside one of the running Pods to verify that the ConfigMap and Secret values were injected correctly into the container process.

kubectl get pods -n demo -l app=web
POD_NAME=$(kubectl get pods -n demo -l app=web -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n demo "$POD_NAME" -- env | grep -E 'APP_ENV|DB_PASSWORD'

Expected output

NAME                   READY   STATUS    RESTARTS   AGE
web-7f89d4b68f-k2l8x   1/1     Running   0          18s
web-7f89d4b68f-w79np   1/1     Running   0          18s
APP_ENV=production
DB_PASSWORD=supersecret

Step 4: Expose the Pods with a stable Service

Every Pod gets its own internal IP address, but those IPs vanish whenever a Pod is recreated. A Service acts as a reliable front door by providing a single stable IP and internal DNS name, load-balancing incoming traffic across any Pod matching the selector label app: web.

kubectl apply -n demo -f - <<EOF
apiVersion: v1
kind: Service
metadata:
  name: web-service
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 80
EOF

Expected output

service/web-service created

Step 5: Test the route and observe self-healing

Now verify that the Service routes traffic to your Pods, then deliberately delete one Pod to see the Deployment replace it instantly. We spin up a temporary curl container inside the cluster to test the Service endpoint, delete a Pod, and confirm traffic never breaks.

kubectl run test-curl --image=curlimages/curl -n demo --rm -i --restart=Never -- curl -s -I http://web-service.demo.svc.cluster.local
kubectl delete pod -n demo "$POD_NAME"
kubectl get pods -n demo -l app=web

Expected output

HTTP/1.1 200 OK
Server: nginx/1.27.0
Content-Type: text/html

pod "web-7f89d4b68f-k2l8x" deleted
NAME                   READY   STATUS    RESTARTS   AGE
web-7f89d4b68f-w79np   1/1     Running   0          65s
web-7f89d4b68f-9z2pq   1/1     Running   0          3s

Why this matters

In production, servers fail, containers crash, and software needs continuous rollouts. If you deploy bare Pods, any node termination takes your service offline permanently.

By tying these five objects together, you build a resilient pipeline. The ConfigMap and Secret allow you to build an image once and run it anywhere without baking passwords into container layers. The Deployment ensures your required scale is maintained automatically. The Service decouples internal routing from ephemeral container IPs. Once you understand this loop, you understand the core architecture of nearly every workload deployed to Kubernetes.

Common mistakes

  • Mismatched selector labels: The Service has selector.app: web while the Deployment template has labels.app: frontend. The symptom is that the Service gets created, but kubectl get endpoints shows <none> and all requests hang or time out. Fix this by ensuring the Service selector keys and values match the Deployment spec.template.metadata.labels block exactly.
  • Missing or misspelled ConfigMap/Secret keys: Referencing a key name in the Deployment YAML that does not exist in the ConfigMap or Secret. The symptom is Pod status showing CreateContainerConfigError. Fix this by running kubectl describe pod <pod-name> -n demo to read the missing key name, then update your ConfigMap or Secret accordingly.
  • Treating Secrets as true encryption by default: Forgetting that vanilla Kubernetes Secrets are simply base64-encoded strings, not encrypted at rest by default. The symptom is sensitive tokens exposed in cleartext to anyone with read access to the namespace. Fix this by integrating an external secret manager or enabling KMS encryption providers on your cluster.

Quick recap

  1. Create a namespace and populate plain values with a ConfigMap and sensitive credentials with a Secret.
  2. Define a Deployment that runs your container image and injects your settings as environment variables.
  3. Verify that your Pods are running and that the configuration is available inside the container runtime.
  4. Expose the dynamic Pod fleet behind a stable ClusterIP Service using label selectors.
  5. Send traffic through the Service DNS name and delete a Pod to prove the Deployment heals itself without downtime.
