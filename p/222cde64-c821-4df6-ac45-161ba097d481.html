If you've ever typed kubectl top and wondered where the numbers come from, stay with me. Here is the honest version. I once spent a whole afternoon guessing how much CPU a service needed, because I didn't know those numbers existed. By the end of this video, you will check cluster usage with a few commands, find the heaviest pod, and understand why autoscaling depends on this API. No theory dump. We go from the question, what is using my CPU, to a working scale-up test in your own cluster. Why this matters. Kubernetes knows where your pods run. It does not know how hungry they are, unless something measures them. The Metrics API is the standard way for Kubernetes to answer one question: how much CPU and memory is this pod or node using right now? Stable here is a promise. The shape of the API stops changing under you, so the tools built on top of it can rely on it. Here is the part most tutorials skip. The Metrics API is only an interface. It is not the thing collecting the data. The collector is metrics-server. It runs as a pod in your cluster, asks each node for usage numbers, and serves them through the Metrics API. The kubelet is the agent running on every node. It already tracks container resource usage, so metrics-server simply reads what is already there. So the chain is simple. Containers, then kubelet, then metrics-server, then the Metrics API, then kubectl top or an autoscaler. Notice what it is not. It is not Prometheus. Prometheus keeps history for dashboards and alerts. The Metrics API gives you right now, and only right now. That one difference explains a lot of beginner confusion. Why does kubectl top show a single number and not a graph? Because it was never built to store the past. What does it measure? Two things, CPU and memory, for nodes and for pods. That is the entire scope. Keep that small scope in mind for the rest of this video. Why does autoscaling care? The Horizontal Pod Autoscaler reads CPU usage from this API. No metrics means no scaling decision. It just sits there. Here is my war story. Once I set up an autoscaler on a fresh cluster, and it did absolutely nothing for an hour. Metrics-server had never been installed. The autoscaler showed unknown for its target. No crash, no stack trace. Just a quiet unknown, which is far harder to spot than an error. The lesson: before you blame your scaling rules, check whether the Metrics API is actually answering. We will check that in the walkthrough. Watch the flow. Each node's kubelet reports usage. Metrics-server collects those reports, and the API serves a fresh snapshot every time something asks. Walkthrough time. Start by confirming your cluster version, so you know exactly what you are testing against. Next, check whether the Metrics API is registered. Kubernetes exposes it as an APIService. If it is listed, the chain is connected. Read the columns. The AVAILABLE column matters most. True means the API is answering. False means something upstream is broken. Now check the collector itself. Metrics-server usually lives in the kube-system namespace, and the official manifests label it with k8s-app equals metrics-server. If that pod is not Running, kubectl top will fail. A healthy pod is your first green light. Next, ask for live node usage. Now run kubectl top nodes. You get CPU and memory for every node, plus the percentage of each node that is in use. CPU shows in millicores. One thousand millicores is one full core. Memory shows in mebibytes or gibibytes. Learn those two units once and they stay useful. Now the pods. Add the all namespaces flag and sort by CPU, so the heaviest workload rises to the top of the list. Sorting by memory works the same way. Swap cpu for memory when you are hunting an out-of-memory problem instead of a slow app. Pods can hold several containers. A sidecar might be eating more CPU than your app. The containers flag breaks usage down per container. The pod name in that command is only an example. Yours will have a different suffix, so run get pods first and copy the real name. Let us prove the numbers change. Start a deliberate load generator. This loop burns CPU forever, so we will delete it at the end. Give it about thirty seconds, then check again. Metrics refresh on an interval, so a brand new pod may show almost nothing at first. Now check the load pod's usage. There it is. CPU climbing toward a full core. This is the Metrics API doing its one job: giving you the snapshot as it is right now. Now connect it to scaling. Assume a deployment called web already exists. We create an autoscaler targeting fifty percent CPU, between two and ten replicas. Watch the autoscaler. The targets column compares current usage against your fifty percent goal. Those current numbers come straight from the Metrics API. Here is the trap. If the Metrics API fails, the autoscaler stops making good decisions. It is only as reliable as the numbers it reads. When metrics-server is down or unhealthy, this is the message you will see. Memorize it. It is the most common Metrics API error beginners hit. That message means kubectl could not reach the aggregated API. Do not start by editing your app. Start from the top of the chain and walk back down. Check whether the APIService is available, then whether the metrics-server pod is running. Then read its logs, which explain why it cannot scrape a node. Now the payoff. As load climbs past the target, the autoscaler adds pods. Each new replica takes its share of traffic until usage settles back down. Now clean up. Delete the load pod, because a busy loop running forever will keep burning CPU on your node until you stop it. Watch the replicas drop. Once usage falls, the autoscaler waits out a short cooldown and then scales back down toward the minimum. Recap, part one. The Metrics API answers one question: how much CPU and memory is this pod or node using right now. Part two. Metrics-server is the collector. If it is down, kubectl top and autoscaling both go quiet at the same time. Part three. When something breaks, walk the chain from the top: APIService, then the pod, then the logs. Not your application code. Here is the one takeaway to remember. Before you tune scaling rules, check that the Metrics API is answering. Write that on a sticky note. If this clicked, subscribe.
