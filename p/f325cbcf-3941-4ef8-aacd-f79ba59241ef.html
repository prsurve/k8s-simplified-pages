ROADMAP

By the end of this guide, you will understand the three core building blocks of Kubernetes—Pods, Deployments, and Services—by creating and connecting them from scratch. Instead of memorizing 40 different API objects, you will see how traffic flows from a network endpoint down into a running container. Mastering this relationship gives you the foundation needed to understand almost every advanced workload in Kubernetes.

Why this matters

Most beginners fail to learn Kubernetes because they treat the documentation like a vocabulary list. In reality, Kubernetes is designed as an onion: a Pod runs your container, a Deployment keeps that Pod alive and handles updates, and a Service gives those Pods a stable network identity. If you cannot trace how these three primitives talk to each other using labels and selectors, learning tools like Helm, Ingress, or Service Meshes will only lead to confusion.

Step 1: Create an isolated namespace

Create a dedicated namespace called demo so that your practice resources do not mix with default workloads and can be wiped clean in a single command later.

kubectl create namespace demo

Expected output

namespace/demo created

Step 2: Run a raw Pod to see the basic unit of compute

A Pod is the smallest deployable object in Kubernetes; it wraps one or more containers, shares storage, and assigns a single internal IP. Run a standalone Pod running nginx:1.27 directly to see what a raw workload looks like before adding management layers.

kubectl run web-pod --image=nginx:1.27 --namespace=demo
kubectl get pods -n demo -o wide

Expected output

pod/web-pod created
NAME      READY   STATUS    RESTARTS   AGE   IP           NODE       NOMINATED NODE   READINESS GATES
web-pod   1/1     Running   0          5s    10.244.0.5   worker-1   <none>           <none>

Step 3: Delete the raw Pod and replace it with a Deployment

Standalone Pods do not self-heal; if the node dies or you manually delete the Pod, it stays gone forever. Delete the manual Pod and create a Deployment named web running nginx:1.27 with 2 replicas so Kubernetes automatically manages Pod lifecycles.

kubectl delete pod web-pod -n demo
kubectl create deployment web --image=nginx:1.27 --replicas=2 -n demo
kubectl get pods -n demo -l app=web

Expected output

pod "web-pod" deleted
deployment.apps/web created
NAME                   READY   STATUS    RESTARTS   AGE
web-78d6494794-4kx2p   1/1     Running   0          6s
web-78d6494794-w9zsl   1/1     Running   0          6s

Step 4: Expose the Deployment with a ClusterIP Service

Pods are ephemeral; when a Pod crashes or rolls out a new version, it gets replaced with a new IP address. Create a Service named web-service targeting port 80, which provisions a stable internal IP address and load-balances traffic across all Pods matching the app=web label.

kubectl expose deployment web --name=web-service --port=80 --target-port=80 -n demo
kubectl get service web-service -n demo

Expected output

service/web-service exposed
NAME          TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
web-service   ClusterIP   10.96.184.212   <none>        80/tcp    4s

Step 5: Verify the traffic path from within the cluster

To confirm the Service correctly routes requests to the Deployment's underlying Pods, run a temporary debug Pod and make an HTTP request to the Service name using Kubernetes internal DNS.

kubectl run curl-test --image=curlimages/curl:8.7.1 --rm -it --restart=Never -n demo -- curl -s -I http://web-service.demo.svc.cluster.local

Expected output

HTTP/1.1 200 OK
Server: nginx/1.27.0
Date: Mon, 16 Sep 2024 12:00:00 GMT
Content-Type: text/html
Content-Length: 615
Connection: keep-alive
pod "curl-test" deleted

Common mistakes

  • Mismatched label selectors: The Service is created, but requests time out or return empty responses. Check kubectl get endpoints web-service -n demo. If the ENDPOINTS column is <none>, the selector inside the Service definition does not match the labels assigned to the Pods in your Deployment.
  • Confusing port with targetPort: The client receives a connection refused error when curling the Service. port defines the port exposed on the Service IP itself, while targetPort must match the port your container process is actually listening on inside the Pod (e.g., port 80 for Nginx).
  • Managing Pods directly in production: A Pod crashes, and your application goes down permanently without recovering. Never write naked Pod manifests for application workloads; always wrap them in a Deployment so the ReplicaSet controller guarantees desired state.

Quick recap

  1. Created an isolated demo namespace to hold all exercise resources safely.
  2. Ran a raw Pod to observe that containers require an enclosing Kubernetes wrapper.
  3. Replaced the raw Pod with a Deployment to unlock declarative replicas and self-healing.
  4. Attached a Service to give the dynamic Pod instances a single, permanent virtual IP and DNS name.
  5. Sent traffic to the Service via internal DNS to verify complete end-to-end connectivity.
