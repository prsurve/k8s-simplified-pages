Your Service looks healthy, your router won't start, and one empty headless Service is the reason.

A Kubernetes Service can look healthy while routing is already broken. That's the trap with a headless Service. A normal Service keeps a stable IP even when no Pods are behind it. A headless Service (cluster IP set to none) returns the ready Pods' addresses directly. With zero Pods, it returns nothing. nginx resolves its upstreams once at startup and exits if a lookup fails, so a fresh router restart can take everything down. ENDPOINTS

By the end of this guide, you will understand why an empty headless Service can crash an NGINX router on startup and how to diagnose the issue instantly. You will deploy a live reproduction of this failure pattern using standard Kubernetes manifests. Mastering this prevents silent, cascading outages when upstream Pods scale to zero.

Why this matters

A standard Kubernetes Service assigns a virtual ClusterIP. Even when zero Pods match its selector, CoreDNS resolves the Service name to that stable IP address, so proxy software like NGINX boots without complaint.

A headless Service sets clusterIP: None, telling CoreDNS to skip the virtual IP and return the individual IP addresses of ready Pods. When no ready Pods exist, DNS queries return an empty NXDOMAIN or NOERROR with no A records. Because standard NGINX configuration resolves upstream domain names strictly during startup, an empty headless Service causes NGINX to fail configuration validation and crash immediately in a CrashLoopBackOff.

Step 1: Create the demo namespace and an empty headless Service

First, create a dedicated namespace called demo and deploy a headless Service that currently selects zero running Pods. We do this to simulate an upstream backend that has scaled down or failed to initialize.

kubectl create namespace demo
kubectl apply -n demo -f - <<EOF
apiVersion: v1
kind: Service
metadata:
  name: backend-headless
spec:
  clusterIP: None
  selector:
    app: backend
  ports:
  - port: 80
    targetPort: 80
EOF

Expected output

namespace/demo created
service/backend-headless created

Step 2: Inspect the headless Service endpoints

Check the Service details and its corresponding Endpoints object to verify what CoreDNS sees. You will notice that while the Service appears healthy in kubectl get svc, the Endpoints resource holds no target addresses.

kubectl get svc,endpoints backend-headless -n demo

Expected output

NAME                           TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)   AGE
service/backend-headless       ClusterIP   None         <none>        80/TCP    18s

NAME                             ENDPOINTS   AGE
endpoints/backend-headless       <none>      18s

Step 3: Deploy NGINX configured with the headless upstream

Now deploy an NGINX router that references backend-headless.demo.svc.cluster.local in its proxy_pass directive. We provide the NGINX configuration via a ConfigMap and mount it into an nginx:1.27 Pod.

kubectl apply -n demo -f - <<EOF
apiVersion: v1
kind: ConfigMap
metadata:
  name: router-config
data:
  default.conf: |
    server {
        listen 80;
        location / {
            proxy_pass http://backend-headless.demo.svc.cluster.local;
        }
    }
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: router
spec:
  replicas: 1
  selector:
    matchLabels:
      app: router
  template:
    metadata:
      labels:
        app: router
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - containerPort: 80
        volumeMounts:
        - name: config
          mountPath: /etc/nginx/conf.d
      volumes:
      - name: config
        configMap:
          name: router-config
EOF

Expected output

configmap/router-config created
deployment.apps/router created

Step 4: Inspect the crashing router logs

Wait a few seconds and inspect the state of the router Pods. NGINX fails its internal configuration syntax validation because it cannot resolve the hostname of the upstream headless Service.

kubectl get pods -n demo -l app=router
kubectl logs -n demo -l app=router --tail=10

Expected output

NAME                      READY   STATUS             RESTARTS      AGE
router-57b9d4dfbc-8wkm9   0/1     CrashLoopBackOff   1 (10s ago)   15s
2025/03/30 12:00:00 [emerg] 1#1: host not found in upstream "backend-headless.demo.svc.cluster.local" in /etc/nginx/conf.d/default.conf:4
nginx: [emerg] host not found in upstream "backend-headless.demo.svc.cluster.local" in /etc/nginx/conf.d/default.conf:4
nginx: configuration file /etc/nginx/nginx.conf test failed

Step 5: Fix the failure by starting a matching backend Pod

Launch a Deployment matching the app: backend selector defined on the headless Service. Once this backend Pod reaches the Ready status, its IP populates the Endpoints object, CoreDNS begins answering queries, and NGINX boots cleanly.

kubectl apply -n demo -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
spec:
  replicas: 1
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
      - name: web
        image: nginx:1.27
        ports:
        - containerPort: 80
EOF
kubectl wait --for=condition=Ready pod -l app=backend -n demo --timeout=30s
kubectl get pods -n demo

Expected output

deployment.apps/backend created
pod/backend-6779878d6b-x27zl condition met
NAME                       READY   STATUS    RESTARTS      AGE
backend-6779878d6b-x27zl   1/1     Running   0             14s
router-57b9d4dfbc-8wkm9    1/1     Running   2 (30s ago)   85s

Common mistakes

  • Checking Service presence instead of Endpoints: Running kubectl get svc shows the Service as existing and healthy even if no backend targets exist. Always run kubectl get endpoints <service-name> or kubectl get endpointslices to confirm targets exist.
  • Using static proxy_pass directives with headless Services: Hardcoding proxy_pass http://headless-svc; forces NGINX to resolve names at startup. Define an internal NGINX variable like set $upstream backend-headless; proxy_pass http://$upstream; combined with the resolver 10.96.0.10; directive (pointing to CoreDNS) to defer DNS lookup to request time.
  • Overlooking restarted containers: Running kubectl logs on a crashing Pod without checking previous runs can show clean initial logs. Always pass the --previous flag (kubectl logs <pod> --previous) if the container has already restarted.

Quick recap

  1. Created an empty headless Service using clusterIP: None.
  2. Verified that the Service exists while the corresponding Endpoints resource remains empty.
  3. Deployed an NGINX router that queries the headless upstream at startup.
  4. Confirmed the router crashed with [emerg] host not found in upstream via Pod logs.
  5. Deployed a matching backend Pod to populate the Endpoints and allow the router to start.
