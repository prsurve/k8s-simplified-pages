Kubernetes was never about containers. It's about who's allowed to control what runs where.

Kubernetes doesn't care about your containers. It cares about who's allowed to control what runs where. Every Kubernetes cluster splits into a control plane (API server, scheduler, etcd) and a data plane (nodes, kubelet, pods) — control plane decides, data plane executes. Scale that same split up and you get platform engineering: a platform team running a management plane on top, giving dev teams their own data plane to ship without waiting on tickets. PLANES

Here's the full breakdown. Every Kubernetes cluster runs on two core planes: (1) Control plane — the API server (front door for every kubectl command), etcd (the source of truth database), scheduler (decides which node a pod lands on), and controller manager (keeps actual state matching desired state). This plane decides. (2) Data plane — your worker nodes, kubelet on each node, kube-proxy for networking, and the actual running pods/containers. This plane executes what the control plane tells it to. As organizations scale to multiple clusters, a third layer shows up: the management/platform plane — tools like Crossplane, Argo CD, or a custom internal developer platform sitting above many clusters, setting policy, RBAC, quotas, and guardrails so a central platform team keeps control while individual dev teams get self-service freedom inside their own data plane. That layered separation — control decides, data executes, platform governs — is what people mean by 'platform sovereignty': every team gets autonomy at their layer without losing central oversight. Whenever you're learning a new K8s feature or tool, ask which plane it lives in and what the blast radius is if that plane fails — it'll make the whole ecosystem click faster than memorizing components in isolation.
