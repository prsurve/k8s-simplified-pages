PART 2

By the end of this guide, you will run a three-machine Kubernetes cluster on your laptop, watch it replace a container that died, spread five copies of an app across machines behind one steady address, and roll out a new version without taking the app down. These four jobs are what turn a container that runs into a service you can depend on.

Step 1: Create a cluster and deploy one app

Kubernetes needs machines to schedule work onto. We will use kind (Kubernetes IN Docker), which runs each cluster node as a Docker container, so you get a realistic multi-node cluster with no cloud account. This config gives you one control plane node and two worker nodes.

kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
- role: worker
- role: worker

Save that as kind-config.yaml and create the cluster. Docker must be running first.

kind create cluster --name demo-cluster --config kind-config.yaml
kubectl get nodes

Expected output

 ✓ Joining worker nodes 🚜
Set kubectl context to "kind-demo-cluster"

Next, create a namespace called demo so your work stays separate, and deploy the app. A Deployment tells Kubernetes what container to run and how many copies should exist.

kubectl create namespace demo
kubectl create deployment web --image=nginx:1.27 -n demo
kubectl get pods -n demo

Expected output

deployment.apps/web created
NAME                   READY   STATUS    RESTARTS   AGE
web-6c8f7d9b5-k4x2m    1/1     Running   0          8s

Step 2: Watch Kubernetes restart a dead container

A bare container stays dead when it crashes. A Deployment keeps comparing the number of running pods to the number you asked for, and it starts a replacement when the count drops. To see this, delete the pod. The -l app=web flag selects pods by label, so you do not need to copy the name.

kubectl delete pod -l app=web -n demo
kubectl get pods -n demo

Expected output

pod "web-6c8f7d9b5-k4x2m" deleted

NAME                   READY   STATUS    RESTARTS   AGE
web-6c8f7d9b5-r9t7v    1/1     Running   0          6s

The old pod is gone and a new one with a different suffix is running. You did not restart anything by hand.

Step 3: Scale to five copies and spread them across machines

Scaling is only useful if the copies land on different machines, so that one machine failing does not take them all down. The YAML below sets five replicas and adds a topologySpreadConstraint, which asks the scheduler to balance pods across nodes. It also adds a Service, which gives the copies one stable address and load-balances traffic across the ready ones.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
spec:
  replicas: 5
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: web
      containers:
      - name: nginx
        image: nginx:1.27
---
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: demo
spec:
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 80

Save it as web.yaml and apply it. Applying updates the Deployment from Step 1 in place.

kubectl apply -f web.yaml
kubectl get pods -n demo -o wide
kubectl get service web -n demo

The pods are split across both workers. The Service's CLUSTER-IP stays the same even when pods come and go.

Now test the networking from inside the cluster. This temporary pod calls the Service by its name.

kubectl run tester --rm -it --image=busybox:1.36 -n demo --restart=Never -- wget -qO- http://web

Expected output

<!DOCTYPE html>
<html>
<head>
<title>Welcome to nginx!</title>
...
</html>

The name web resolves through cluster DNS to the Service, which sends the request to a healthy pod.

Step 4: Roll out a new version gradually

Changing the image in a Deployment triggers a rolling update. Kubernetes starts new pods on the new version and stops old ones in small batches, so some copies always serve traffic. Here we move from nginx:1.27 to nginx:1.26 and watch it happen.

kubectl set image deployment/web nginx=nginx:1.26 -n demo
kubectl rollout status deployment/web -n demo

Expected output

deployment.apps/web image updated
Waiting for deployment "web" rollout to finish: 2 out of 5 new replicas have been updated...
Waiting for deployment "web" rollout to finish: 3 out of 5 new replicas have been updated...
Waiting for deployment "web" rollout to finish: 4 out of 5 new replicas have been updated...
deployment "web" successfully rolled out

Confirm the running image:

kubectl get deployment web -n demo -o jsonpath='{.spec.template.spec.containers[0].image}'

Expected output

nginx:1.26

If something goes wrong, kubectl rollout undo deployment/web -n demo returns the Deployment to the previous version.

Common mistakes

  • Running a bare pod instead of a Deployment. The symptom is that the pod is gone for good after you delete it or it crashes. The fix is to create a Deployment, which recreates pods to match the replica count.
  • Forgetting the namespace flag. The symptom is No resources found in default namespace. even though you just created the pods. The fix is to add -n demo to every command, or set a default with kubectl config set-context --current --namespace=demo.
  • Calling a pod IP instead of the Service name. Pod IPs change every time a pod is replaced, so the address breaks after a restart. The fix is to use the Service name, such as http://web, which stays stable.
  • Starting kind without Docker running. The symptom is Cannot connect to the Docker daemon during cluster creation. The fix is to start Docker and run the create command again.

Quick recap

  1. Create a multi-node cluster with kind and confirm the nodes are Ready.
  2. Deploy web with a Deployment so Kubernetes manages the pods.
