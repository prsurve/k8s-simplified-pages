CHECKPOINT

In distributed training, losing a single worker halts your entire job because all nodes must stay synchronized. If that replacement worker starts without state, hours of expensive GPU compute vanish into thin air. By the end of this guide, you will be able to configure shared persistent storage across multi-worker training jobs so crashed pods recover immediately from the latest checkpoint.

Why this matters

Distributed training frameworks like PyTorch Distributed Data Parallel (DDP) run workers that process different batches of data in parallel. At the end of every forward and backward pass, the workers must communicate to synchronize gradients before updating the model weights. If worker 3 crashes—often due to an out-of-memory error causing an exit code 137—the other seven workers block indefinitely while waiting for it to report in.

When Kubernetes restarts that failed pod, the pod arrives with a clean local disk. If your training script was saving checkpoint weights to the pod's local directory, those weights are gone. The revived pod must start at step zero, which either desynchronizes the cluster or forces the entire job to restart from scratch. To prevent this, your checkpoints must live on a shared PersistentVolume accessible by every worker.

Step 1: Create a shared namespace

Create a dedicated namespace called ai-workloads so all resources stay grouped together. This isolates your storage and workloads from default cluster operations.

kubectl create namespace ai-workloads

Expected output

namespace/ai-workloads created

Step 2: Request ReadWriteMany storage

Create a PersistentVolumeClaim named checkpoint-pvc with ReadWriteMany access mode. This mode allows all training pods to attach to the same volume simultaneously and write their checkpoint files.

Save the following manifest to pvc.yaml and apply it:

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: checkpoint-pvc
  namespace: ai-workloads
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 50Gi
kubectl apply -f pvc.yaml

Expected output

persistentvolumeclaim/checkpoint-pvc created

Step 3: Verify the claim is bound

Check the status of your volume claim before launching workloads to ensure the cluster has provisioned underlying shared storage. A claim stuck in Pending means your storage class cannot support multiple simultaneous mounts.

kubectl get pvc checkpoint-pvc -n ai-workloads

Expected output

NAME             STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
checkpoint-pvc   Bound    pvc-8b1a3d90-34fa-4ce2-b2d4-1a5c8e390ab1   50Gi       RWX            nfs-client     12s

Step 4: Run a multi-worker job mounting the volume

Deploy an indexed Kubernetes Job named distributed-training with two worker completions. Each pod mounts the shared PVC at /checkpoints, where training loops read and write saved state.

Save the following manifest to job.yaml and apply it:

apiVersion: batch/v1
kind: Job
metadata:
  name: distributed-training
  namespace: ai-workloads
spec:
  completions: 2
  parallelism: 2
  completionMode: Indexed
  template:
    metadata:
      labels:
        app: training-worker
    spec:
      restartPolicy: OnFailure
      containers:
      - name: worker
        image: python:3.11-slim
        command: ["/bin/sh", "-c"]
        args:
          - |
            echo "Checking for latest checkpoint on shared volume...";
            ls -l /checkpoints;
            echo "Worker $JOB_COMPLETION_INDEX writing step 500 state...";
            echo "weights_step_500" > /checkpoints/model_worker_${JOB_COMPLETION_INDEX}.pt;
            sleep 10;
        volumeMounts:
        - name: checkpoint-storage
          mountPath: /checkpoints
      volumes:
      - name: checkpoint-storage
        persistentVolumeClaim:
          claimName: checkpoint-pvc
kubectl apply -f job.yaml

Expected output

job.batch/distributed-training created

Step 5: Verify checkpoint persistence across workers

Check the log output of one of the completed pods to confirm it mounted the shared path and saved its checkpoint file.

kubectl logs distributed-training-0-0 -n ai-workloads

Expected output

Checking for latest checkpoint on shared volume...
total 0
Worker 0 writing step 500 state...

Inspect the second worker to confirm both workers operated against the same shared storage location.

kubectl logs distributed-training-1-1 -n ai-workloads

Expected output

Checking for latest checkpoint on shared volume...
-rw-r--r-- 1 root root 17 May 10 14:00 model_worker_0.pt
Worker 1 writing step 500 state...

Common mistakes

  • Using ReadWriteOnce instead of ReadWriteMany: The first pod mounts the volume successfully, but subsequent pods on different nodes stay stuck in ContainerCreating with FailedMount warnings. Always ensure your storage class supports multi-node read-write access.
  • Writing to container local storage: Storing checkpoints in an unmounted path like /tmp or the working directory causes data loss when a pod restarts. Ensure your application checkpointing logic writes explicitly to the mounted path.
  • Hardcoding checkpoint filenames without epochs: Overwriting a single model.pt file can corrupt weights if a pod crashes midway through a write operation. Save checkpoints with step numbers, like model_step_100.pt, and implement an atomic rename.
  • Setting restart policies to Never: If a training pod crashes under restartPolicy: Never, Kubernetes marks the pod failed and will not restart it, leaving remaining workers blocked indefinitely. Use restartPolicy: OnFailure.

Quick recap

  1. Create a dedicated ai-workloads namespace to isolate distributed training components.
  2. Define a PersistentVolumeClaim with ReadWriteMany access so multiple nodes can read and write simultaneously.
  3. Validate that your storage provider binds the claim properly before deploying pods.
  4. Mount the persistent volume to /checkpoints across all workers in your training job manifest.
  5. Verify that each worker reads and writes persistent state directly to the shared volume path.
