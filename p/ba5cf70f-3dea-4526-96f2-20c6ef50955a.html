MEMORY

When a Java container dies in Kubernetes, your monitoring dashboards often show heap utilization hovering safely at 50% or 60%. This guide shows you how to determine whether the Linux kernel killed your pod due to container memory exhaustion and how to correctly size JVM memory beyond the heap. By the end, you will be able to diagnose exit code 137, inspect non-heap overhead, and configure production-safe resource limits.

Why this matters

A Java process consumes far more than just the heap defined by -Xmx. The JVM requires memory for Metaspace (loaded class metadata), thread stacks, the JIT code cache, and off-heap direct byte buffers commonly used by network clients like Netty. Kubernetes enforces resource limits at the cgroup level, which tracks the resident set size (RSS) of the entire container process. If heap plus non-heap memory exceeds your container's resources.limits.memory, the Linux Out-Of-Memory (OOM) killer terminates the process instantly with SIGKILL (kill -9), preventing Java from logging an OutOfMemoryError.

Step 1: Verify the OOMKilled state and exit code

Check the status of your crashing pod using kubectl describe to see if the kernel terminated the container. This confirms whether the issue is a cgroup limit breach rather than an internal JVM crash.

kubectl describe pod web-789c679b8d-2k9jl -n demo

Expected output

    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
      Started:      Mon, 21 Apr 2025 10:14:20 +0000
      Finished:     Mon, 21 Apr 2025 10:22:45 +0000

Step 2: Track total container memory against the limit

Run kubectl top pod to see the actual resident memory consumption of the pod in real time before it crashes. Compare this value to the limit set in the pod specification rather than relying strictly on JVM application metrics.

kubectl top pod web-789c679b8d-2k9jl -n demo

Expected output

NAME                     CPU(cores)   MEMORY(bytes)   
web-789c679b8d-2k9jl     45m          982Mi

Step 3: Enable Native Memory Tracking to inspect off-heap usage

Add JVM flags to your deployment to enable Native Memory Tracking (NMT) so you can measure how much memory is consumed outside the heap. Set -XX:NativeMemoryTracking=summary in your Java startup options to see allocations for Metaspace, threads, and internal symbols.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
spec:
  replicas: 1
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: spring-app
        image: eclipse-temurin:21-jre-alpine
        command: ["java"]
        args:
        - "-XX:NativeMemoryTracking=summary"
        - "-jar"
        - "/app/app.jar"
        resources:
          requests:
            memory: "1Gi"
          limits:
            memory: "1Gi"

Expected output

deployment.apps/web configured

Step 4: Inspect off-heap allocations using jcmd

Execute jcmd inside the running container to print the native memory breakdown while the service is handling traffic. This exposes the real cost of non-heap components like class metadata, thread stacks, and network buffers.

kubectl exec -n demo deploy/web -- jcmd 1 VM.native_memory summary

Expected output

Total: reserved=1420MB, committed=910MB
-                 Java Heap (reserved=512MB, committed=512MB)
-                    Class (reserved=108MB, committed=45MB)
-                   Thread (reserved=62MB, committed=62MB)
-                     Code (reserved=48MB, committed=35MB)
-                       GC (reserved=95MB, committed=95MB)
-                 Internal (reserved=140MB, committed=140MB)

Step 5: Adjust the container limit to accommodate total JVM overhead

Calculate your required container memory limit using the formula: Heap + Metaspace + (Thread Count × Stack Size) + Direct Buffers + Headroom. Update the deployment manifest so the cgroup limit accommodates both the heap and the non-heap allocations.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
spec:
  template:
    spec:
      containers:
      - name: spring-app
        image: eclipse-temurin:21-jre-alpine
        command: ["java"]
        args:
        - "-XX:MaxRAMPercentage=65.0"
        - "-XX:MaxMetaspaceSize=128m"
        - "-jar"
        - "/app/app.jar"
        resources:
          requests:
            memory: "1536Mi"
          limits:
            memory: "1536Mi"

Expected output

deployment.apps/web configured

Common mistakes

  • Allocating 80% to 90% of the container limit to the heap via -XX:MaxRAMPercentage or -Xmx. This leaves insufficient space for Metaspace, thread stacks, and direct memory. The kernel invokes the OOM killer when the total process size exceeds the remaining 10%. Reserve at least 25% to 35% of container memory for non-heap usage.
  • Assuming an application OutOfMemoryError will always appear in pod logs. When the cgroup memory limit is exceeded, the Linux kernel terminates the process instantly with SIGKILL. The JVM gets no opportunity to intercept the signal or dump an error. Always verify the status via kubectl describe pod.
  • Uncapped direct byte buffers in high-throughput network applications. Frameworks like Netty allocate off-heap buffers for network I/O, which default to the max heap size if left unconstrained. Limit direct buffer memory explicitly using -XX:MaxDirectMemorySize to prevent unexpected growth.

Quick recap

  1. Run kubectl describe pod to verify termination reason OOMKilled and exit code 137.
  2. Check total resident memory consumption using kubectl top pod.
  3. Enable Native Memory Tracking on the container with -XX:NativeMemoryTracking=summary.
  4. Run jcmd 1 VM.native_memory summary to measure committed off-heap memory.
  5. Set resources.limits.memory higher than the combined sum of heap, Metaspace, threads, and off-heap buffers.
