PART 2

This guide shows you how to ask Kubernetes for a set of containers, change how many run, and watch it repair the count when one disappears. By the end, you will have run a small web app across a group of machines without choosing any machine yourself, which is the job I did by hand with a spreadsheet.

Step 1: Create a namespace and a deployment

First, make a separate area in the cluster called demo so the lab stays tidy. Then describe your desired state in a file: a deployment named web, using the nginx:1.27 image, with three copies. A deployment is the object that keeps a count of your containers for you.

kubectl create namespace demo

Expected output

namespace/demo created

Next, save this manifest as web.yaml. It says what you want, and it says nothing about which machine should run each copy.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27

Apply it, then list the Pods. Each copy runs as a Pod, a small wrapper around one container, and Kubernetes places each Pod on a node with room.

kubectl apply -f web.yaml
kubectl get pods -n demo -o wide

Expected output

deployment.apps/web created
NAME                   READY   STATUS    RESTARTS   AGE   IP            NODE       NOMINATED NODE   READINESS GATES
web-6f9c7b8d4-2kq7m    1/1     Running   0          12s   10.244.1.5    node-1     <none>           <none>
web-6f9c7b8d4-8vx4t    1/1     Running   0          12s   10.244.2.7    node-2     <none>           <none>
web-6f9c7b8d4-rn5zl    1/1     Running   0          12s   10.244.3.4    node-3     <none>           <none>

Notice the spread. The NODE column shows three different machines, so no single machine holds the whole app. You typed none of those generated names.

Step 2: Scale up by changing one number

Traffic is climbing, so you need five copies. Instead of copying containers onto servers, change the replica count and let Kubernetes find room for the new Pods. The scale command is the quickest way to do this.

kubectl scale deployment web --replicas=5 -n demo
kubectl get pods -n demo -o wide

Expected output

deployment.apps/web scaled
NAME                   READY   STATUS    RESTARTS   AGE   IP            NODE       NOMINATED NODE   READINESS GATES
web-6f9c7b8d4-2kq7m    1/1     Running   0          2m    10.244.1.5    node-1     <none>           <none>
web-6f9c7b8d4-8vx4t    1/1     Running   0          2m    10.244.2.7    node-2     <none>           <none>
web-6f9c7b8d4-rn5zl    1/1     Running   0          2m    10.244.3.4    node-3     <none>           <none>
web-6f9c7b8d4-hd8bq    1/1     Running   0          8s    10.244.1.6    node-1     <none>           <none>

Two new Pods appeared, and you did not open a spreadsheet or log into a server. You changed a number, and the platform did the placing.

Step 3: Delete a Pod and watch the count repair itself

This is the failure that caused my 3 AM outage: a copy disappears. In a lab, you can simulate it by deleting one Pod on purpose. Do not do this casually in production. Start by listing the Pods so you can pick a name.

kubectl get pods -n demo
kubectl delete pod web-6f9c7b8d4-2kq7m -n demo
kubectl get pods -n demo

Why this matters

My outage was a count problem. A machine dropped out, its copy vanished, and nothing noticed for forty minutes because nothing was checking the number. A deployment does that check continuously. It compares the count you asked for with what is actually running, and it acts when they differ. The three commands you just ran show the whole loop: declare the count, let the platform place it, and let the platform repair it.

Common mistakes

  • Forgetting the namespace. You run kubectl get pods and see No resources found. The symptom is that your Pods exist but are invisible to the command. The fix is to add -n demo to every command in this guide.
  • Editing the Pod instead of the deployment. You change a Pod's setting, but the Pod is replaced the moment it is deleted, so the change vanishes. The fix is to change the deployment, either in web.yaml followed by kubectl apply -f web.yaml, or with kubectl scale.
  • Expecting a deleted Pod to stay gone. You delete a Pod and think you broke the app, then the count is back to normal. The symptom is a new Pod with a new name. This is expected behaviour. The fix is to check the replica count with kubectl get deployment web -n demo, not individual Pod names.
  • Asking for more copies than the machines can hold. Pods sit in Pending forever. The symptom appears in kubectl get pods as STATUS Pending. The fix is to free up room on the nodes or request less memory per container, then check again with kubectl describe pod <pod-name> -n demo to read the scheduling reason.

Quick recap

  1. Create a namespace with kubectl create namespace demo.
  2. Describe the deployment web in web.yaml, with image nginx:1.27 and three replicas.
  3. Apply it with kubectl apply -f web.yaml and check the Pods with kubectl get pods -n demo -o wide.
  4. Scale to five with kubectl scale deployment web --replicas=5 -n demo.
  5. Delete one Pod and confirm that Kubernetes starts a replacement and restores the count to five.
