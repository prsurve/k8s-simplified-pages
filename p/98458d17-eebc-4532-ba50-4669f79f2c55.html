QUEUE

Kueue gives your GPU jobs a queue, so a job waits its turn instead of sitting in Pending with no explanation. By the end, you'll have Kueue installed, a GPU quota for a team, and a training job that gets admitted or waits in a visible queue. This matters because without a queue, the scheduler admits whichever pod arrives first, and nobody can say who should wait or why.

Step 1: Install Kueue

Kueue runs as its own controller in the cluster. You install it once, then check that its pods are running before you create anything else. This guide uses v0.9.1 as an example. Check the Kueue releases page for the current version and substitute it.

kubectl apply --server-side -f https://github.com/kubernetes-sigs/kueue/releases/download/v0.9.1/manifests.yaml
kubectl get pods -n kueue-system

Expected output

namespace/kueue-system serverside-applied
customresourcedefinition.apiextensions.k8s.io/clusterqueues.kueue.x-k8s.io serverside-applied
...
NAME                                        READY   STATUS    RESTARTS   AGE
kueue-controller-manager-7d9f8c6b5-x2vqk    2/2     Running   0          45s

Step 2: Define the GPU quota with a ResourceFlavor and ClusterQueue

A ResourceFlavor describes a kind of hardware, and a ClusterQueue holds the quota for it. This example uses the default flavor, with no special node labels, and gives the queue 8 nvidia.com/gpu in total, which matches the cluster in the post. Kueue's API is in kueue.x-k8s.io/v1beta1, so check your version's docs if the API version differs.

apiVersion: kueue.x-k8s.io/v1beta1
kind: ResourceFlavor
metadata:
  name: default-flavor
---
apiVersion: kueue.x-k8s.io/v1beta1
kind: ClusterQueue
metadata:
  name: cq-gpu
spec:
  namespaceSelector: {}
  resourceGroups:
  - coveredResources: ["cpu", "memory", "nvidia.com/gpu"]
    flavors:
    - name: default-flavor
      resources:
      - name: "cpu"
        nominalQuota: 32
      - name: "memory"
        nominalQuota: 256Gi
      - name: "nvidia.com/gpu"
        nominalQuota: 8

Save this as gpu-queues.yaml and apply it:

kubectl apply -f gpu-queues.yaml

Expected output

resourceflavor.kueue.x-k8s.io/default-flavor created
clusterqueue.kueue.x-k8s.io/cq-gpu created

Step 3: Create a LocalQueue in the team's namespace

Teams submit jobs through a LocalQueue, which lives in a namespace and points to a ClusterQueue. Jobs in demo that name team-a will draw from cq-gpu. Create the namespace first, then the LocalQueue.

kubectl create namespace demo
apiVersion: kueue.x-k8s.io/v1beta1
kind: LocalQueue
metadata:
  name: team-a
  namespace: demo
spec:
  clusterQueue: cq-gpu

Save this as team-a-localqueue.yaml and apply it:

kubectl apply -f team-a-localqueue.yaml

Expected output

namespace/demo created
localqueue.kueue.x-k8s.io/team-a created

Step 4: Submit a labeled GPU job and watch the queue

Kueue only manages a Job that has the label kueue.x-k8s.io/queue-name, and it only admits a Job that starts suspended. Setting suspend: true keeps the pod from being created until Kueue admits it. This job asks for all 8 GPUs, so it takes the whole quota. Save it as train-job-one.yaml.

apiVersion: batch/v1
kind: Job
metadata:
  name: train-job-one
  namespace: demo
  labels:
    kueue.x-k8s.io/queue-name: team-a
spec:
  suspend: true
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: trainer
        image: nvidia/cuda:12.4.1-base-ubuntu22.04
        command: ["sh", "-c", "sleep 300"]
        resources:
          requests:
            nvidia.com/gpu: 8
          limits:
            nvidia.com/gpu: 8

Apply it, then submit a second job with the same spec but a different name, train-job-two, and save it as train-job-two.yaml. Then check the queue:

kubectl apply -f train-job-one.yaml
kubectl apply -f train-job-two.yaml
kubectl get jobs -n demo
kubectl get workloads -n demo

Expected output

job.batch/train-job-one created
job.batch/train-job-two created
NAME            STATUS      COMPLETIONS   DURATION   AGE
train-job-one   Running     0/1           12s        12s
train-job-two   Suspended   0/1                      11s

NAME                          QUEUE    ADMITTED BY   AGE
job-train-job-one-5c1a2       team-a   cq-gpu        12s
job-train-job-two-9e4d7       team-a                 11s

Job one was admitted and job two waits. Job two has no ADMITTED BY value, which tells you it is queued, not broken. When job one finishes, Kueue admits job two:

kubectl get clusterqueue cq-gpu

Expected output

NAME     COHORT   PENDING WORKLOADS   ADMITTED WORKLOADS
cq-gpu            1                   1

Why this matters

Without Kueue, a GPU job that asks for more than is free simply sits in Pending, and the reason is buried in pod events. With Kueue, the waiting job is a Workload inside a named queue, with a clear state you can read. That lets your team see who holds the GPUs, who is waiting, and when quota is returned. It also stops one team's large job from quietly starving everyone else.

Common mistakes

  • The job runs right away and ignores the queue. The symptom is that the job starts without appearing under any Workload. The fix is to add kueue.x-k8s.io/queue-name: team-a to the Job's metadata.labels, not to the pod template.
  • The Job is created but never queued, and no Workload appears. The symptom is an empty kubectl get workloads output for the namespace. The fix is to set spec.suspend: true on the Job so Kueue can take control before the pods start.
  • The Job is stuck and says the queue does not exist. The symptom is no admission, with the Job never leaving its suspended state. The fix is to check that the LocalQueue name in the label matches metadata.name in team-a-localqueue.yaml, and that the LocalQueue exists in the same namespace as the Job.
  • GPU requests are rejected or never fit. The symptom is a Job that waits forever. The fix is to set limits equal to requests for nvidia.com/gpu, and to make sure the ClusterQueue's nominalQuota for that resource is not smaller than the job asks for.
  • Someone deletes the LocalQueue while jobs are running. The symptom is that new jobs stop being admitted. The fix is to keep the queue manifests in version control and reapply them, rather than editing them by hand in the cluster.

Quick recap

  1. Install Kueue and confirm kueue-controller-manager is running in kueue-system.
  2. Create a ResourceFlavor and a ClusterQueue with a fixed nvidia.com/gpu quota.
  3. Create a namespace and a LocalQueue that points to the ClusterQueue.
  4. Submit GPU Jobs with the queue-name label and suspend: true, then check kubectl get workloads and kubectl get clusterqueue.
