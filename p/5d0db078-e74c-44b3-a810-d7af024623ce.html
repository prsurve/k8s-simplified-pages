STATE

In this guide, you will see exactly how Kubernetes handles desired state versus actual state on a live cluster. By deploying a real application, breaking it on purpose, and watching Kubernetes fix it automatically, you will understand the reconciliation loop that powers all of Kubernetes. This mental model will make every YAML manifest you write in your DevOps career make sense.

Step 1: Create a dedicated namespace

We need an isolated space so our experiments do not interfere with other workloads. Namespaces let you group resources together cleanly and delete them in one command when finished.

kubectl create namespace demo

Expected output

namespace/demo created

Step 2: Define your desired state in a YAML file

Instead of telling the cluster step-by-step instructions to launch containers, you write a manifest describing the final result you want. Save this file as web-deployment.yaml. It states that the desired state for our application is exactly three replicas running nginx:1.27.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27

Expected output

web-deployment.yaml created

Step 3: Apply the desired state to the cluster

You use kubectl apply to submit your manifest to the Kubernetes API server. Kubernetes stores this declaration in its database (etcd) as the target truth and instructs the controller manager to create the pods.

kubectl apply -f web-deployment.yaml

Expected output

deployment.apps/web created

Verify that reality now matches your desired state by listing the running pods in the namespace.

kubectl get pods -n demo

Expected output

NAME                   READY   STATUS    RESTARTS   AGE
web-68449757f4-4k9pl   1/1     Running   0          12s
web-68449757f4-8zvwx   1/1     Running   0          12s
web-68449757f4-lq2m8   1/1     Running   0          12s

Step 4: Break reality to watch self-healing

The reconciliation loop constantly asks: does the actual state match the desired state? To see this in action, manually delete one of the running pods using its specific name from the previous step.

kubectl delete pod web-68449757f4-4k9pl -n demo

Expected output

pod "web-68449757f4-4k9pl" deleted

Check your pods immediately after deleting it. Kubernetes noticed that reality had dropped to two pods when the desired count was three, so it immediately scheduled a brand-new pod to replace it.

kubectl get pods -n demo

Expected output

NAME                   READY   STATUS    RESTARTS   AGE
web-68449757f4-8zvwx   1/1     Running   0          45s
web-68449757f4-j9t2c   1/1     Running   0          3s
web-68449757f4-lq2m8   1/1     Running   0          45s

Step 5: Update the desired state declaratively

If you want fewer pods, you do not issue a command to stop one specific container. Instead, you update your declaration in web-deployment.yaml by changing replicas: 3 to replicas: 2, and apply the file again.

sed -i 's/replicas: 3/replicas: 2/' web-deployment.yaml
kubectl apply -f web-deployment.yaml

Expected output

deployment.apps/web configured

Confirm that Kubernetes detected the new target state and terminated the extra pod to bring reality down to two.

kubectl get pods -n demo

Expected output

NAME                   READY   STATUS        RESTARTS   AGE
web-68449757f4-8zvwx   1/1     Running       0          90s
web-68449757f4-j9t2c   1/1     Terminating   0          48s
web-68449757f4-lq2m8   1/1     Running       0          90s

Why this matters

In traditional infrastructure, operations teams rely on imperative scripts filled with sequential commands: start server, check status, configure network. If a step fails halfway through, the script crashes, leaving the system in an unknown, broken state.

Kubernetes replaces that fragility with a continuous loop called reconciliation. You declare what the system should look like, and specialized controllers continuously compare desired state against actual state. If a node dies, a process crashes, or someone deletes a resource, the system does not wait for a human operator or an alert script. It actively drives reality back toward the specification you wrote.

Common mistakes

  • Editing live resources imperatively with kubectl scale while keeping outdated numbers in Git. Symptom: The next CI/CD run or kubectl apply overwrites the manual changes unexpectedly. Fix: Always update the YAML file in source control first, then apply the file.
  • Confusing pod deletion with stopping an application. Symptom: A developer runs kubectl delete pod to halt traffic, but a new pod starts immediately. Fix: Scale the deployment replicas field to 0 or delete the deployment resource entirely.
  • Treating Kubernetes YAML files like procedural scripts that run top-to-bottom. Symptom: Expecting resources defined at the top of a file to finish initializing before resources at the bottom are submitted. Fix: Remember that manifests declare relationships and targets; use readiness probes and proper dependencies instead of file ordering.

Quick recap

  1. Create a clean namespace to isolate your workloads.
  2. Define the desired end result inside a declarative YAML file.
  3. Apply the file using kubectl apply so the cluster stores the target state.
  4. Observe the control loop automatically replace lost pods when actual state deviates.
  5. Change your declared values in YAML and reapply to safely alter the running system.
