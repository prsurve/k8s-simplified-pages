DR

In this guide, you will learn how to handle the three most common Kubernetes disaster recovery scenarios: an etcd crash, a dead worker node, and an accidentally deleted namespace. Beginners often assume Kubernetes will magically rebuild everything on its own, but it cannot recover what it does not remember. By the end of this walkthrough, you will know how to back up your cluster state, simulate failures safely, and restore workloads in minutes.

Why this matters

Your cluster stores every single Deployment, Secret, ConfigMap, and Service inside etcd, a key-value store running on your control plane. If etcd is corrupted or a namespace is deleted, kubectl cannot help you unless you have an external backup or your YAML manifests committed to Git. Disaster recovery is not about hoping your nodes never fail; it is about having a tested command sequence ready before an outage happens.

Step 1: Back up the etcd database snapshot

Capture the current state of your cluster by creating an etcd snapshot using etcdctl. This creates a point-in-time copy of your cluster database that you can restore if the control plane fails or data is corrupted.

ETCDCTL_API=3 etcdctl snapshot save /tmp/etcd-backup.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

Expected output

Snapshot saved at /tmp/etcd-backup.db

Step 2: Verify the snapshot integrity

Inspect the snapshot file you just created to make sure the data is intact and readable before storing it in offsite storage. An unverified backup file is useless if it was corrupted mid-write.

ETCDCTL_API=3 etcdctl snapshot status /tmp/etcd-backup.db --write-out=table

Expected output

+----------+----------+------------+------------+
|   HASH   | REVISION | TOTAL KEYS | TOTAL SIZE |
+----------+----------+------------+------------+
| 3f8b1a9c |     1420 |       1048 |     2.8 MB |
+----------+----------+------------+------------+

Step 3: Simulate and observe a dead worker node

Simulate a node failure by draining a worker node to see how Kubernetes redistributes workloads to healthy nodes. When a node stops responding in production, Kubernetes waits for a timeout period (default 5 minutes) before evicting pods and scheduling them elsewhere.

kubectl drain node-02 --ignore-daemonsets --delete-emptydir-data --force

Expected output

node/node-02 cordoned
evicting pod default/web-7798b64b97-9kldx
pod/web-7798b64b97-9kldx evicted
node/node-02 drained

Step 4: Accidental namespace deletion and Git-based recovery

Create a test namespace named demo running an nginx:1.27 deployment, delete the namespace, and immediately bring it back using your declarative manifest file. Deleting a namespace permanently removes every resource inside it, meaning Git or etcd snapshots are your only recovery path.

kubectl create namespace demo
kubectl create deployment web --image=nginx:1.27 -n demo
kubectl delete namespace demo

Expected output

namespace/demo created
deployment.apps/web created
namespace "demo" deleted

Now, re-apply the workload from your declarative YAML file to restore the entire namespace state instantly.

cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Namespace
metadata:
  name: demo
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
EOF

Expected output

namespace/demo created
deployment.apps/web created

Step 5: Verify the restored deployment

Confirm that your recovered pods are running cleanly in the restored namespace. Always check both pod status and ready counts to verify that recovery succeeded.

kubectl get pods -n demo -l app=web

Expected output

NAME                   READY   STATUS    RESTARTS   AGE
web-7798b64b97-j2b8w   1/1     Running   0          12s
web-7798b64b97-xz9qp   1/1     Running   0          12s

Common mistakes

  • Storing the snapshot on the control plane node itself: When the control plane disk corrupts or terminates, the backup is destroyed with it. Fix: Copy /tmp/etcd-backup.db to object storage like AWS S3 or an isolated backup server immediately after generation.
  • Running etcdctl without API version 3: By default, older etcdctl binaries might use API version 2, producing an error like client: etcd cluster is unavailable or misconfigured. Fix: Always prefix your command with ETCDCTL_API=3.
  • Relying on imperative kubectl create commands during setup: If you build clusters with manual commands, you have no record to re-run when an entire namespace disappears. Fix: Store all configurations as YAML in a Git repository and deploy using kubectl apply -f.
  • Forgetting uncordon after node maintenance: Leaving a node cordoned prevents Kubernetes from scheduling replacement pods onto it. Fix: Run kubectl uncordon node-02 as soon as the node is back online.

Quick recap

  1. Save a point-in-time copy of your cluster database using etcdctl snapshot save.
  2. Validate that your snapshot is not corrupted with etcdctl snapshot status.
  3. Handle node maintenance safely using kubectl drain to evict workloads gracefully.
  4. Keep all application manifests in Git so an accidentally deleted namespace can be recreated in seconds.
  5. Verify application readiness with kubectl get pods after any recovery operation.
