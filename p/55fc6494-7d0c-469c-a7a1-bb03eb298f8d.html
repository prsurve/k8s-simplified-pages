We ran Dragonfly without persistence and cut our image pull times by 70%

We ran Dragonfly without Redis and cut image pull times by 70%. Most teams think Dragonfly needs a full database stack for caching. It doesn't. The P2P distribution is the feature — Redis is only needed if you want persistence across node restarts. For dev and staging clusters, deploy the daemonset in-memory mode and let nodes share layers directly. We went from 4-minute cold starts to 90 seconds with zero database overhead. If you're evaluating Dragonfly for Kubernetes image acceleration, start without Redis. Add it later if prod traffic proves you need it. Drop 'DRAGONFLY' below if you want the full in-memory deployment config. — @k8s.simplified · Kubernetes without the complexity

DRAGONFLY

Here's the lightweight Dragonfly deployment config for in-memory P2P caching without Redis: Add the Dragonfly Helm repo: helm repo add dragonfly https://dragonflyoss.github.io/helm-charts/ helm repo update Install with Redis disabled: helm install dragonfly dragonfly/dragonfly --set redis.enabled=false --set dfdaemon.config.proxy.registryMirror.url=https://index.docker.io This deploys a daemonset on every node. Each node caches pulled image layers in-memory and shares them peer-to-peer with other nodes in the cluster. Update your container runtime to use Dragonfly as a registry mirror by adding this to containerd config.toml: [plugins.'io.containerd.grpc.v1.cri'.registry.mirrors.'docker.io'] endpoint = ['http://127.0.0.1:65001'] Restart containerd, then test with a multi-node deployment: kubectl create deployment nginx --replicas=5 --image=nginx:latest Watch the pull times drop as nodes share layers. For prod, you can add Redis persistence later with --set redis.enabled=true, but start without it to prove the P2P value first.
