PRIORITY

In this guide, you will learn how Kubernetes in-place pod resizing works, how to check its real-time status, and how priority preemption behaves when node resources run tight. Understanding these mechanics ensures you can scale running workloads safely without accidentally evicting critical neighbour pods on the same node.

Step 1: Create a priority class and namespace

Before scheduling pods, configure a custom PriorityClass so Kubernetes knows which workloads have precedence during resource contention. This sets up the exact conditions under which the scheduler decides whether to evict or wait.

kubectl create namespace demo
kubectl apply -f - <<EOF
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
description: "Mission critical web pods"
EOF

Expected output

namespace/demo created
priorityclass.scheduling.k8s.io/high-priority created

Step 2: Deploy a baseline pod with resize policies

Deploy an Nginx pod in the demo namespace configured with resizePolicy. Setting restartPolicy: NotRequired tells the kubelet to adjust CPU allocations dynamically without stopping the container.

kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: demo
spec:
  priorityClassName: high-priority
  containers:
  - name: nginx
    image: nginx:1.27
    resizePolicy:
    - resourceName: cpu
      restartPolicy: NotRequired
    - resourceName: memory
      restartPolicy: NotRequired
    resources:
      requests:
        cpu: "250m"
        memory: "256Mi"
      limits:
        cpu: "500m"
        memory: "512Mi"
EOF

Expected output

pod/web created

Step 3: Trigger an in-place resource resize

Patch the running pod's resource requests directly to demand more CPU. Kubernetes will attempt to resize the running container on its current node without rescheduling or terminating it.

kubectl patch pod web -n demo --patch '{"spec":{"containers":[{"name":"nginx","resources":{"requests":{"cpu":"2000m"},"limits":{"cpu":"2000m"}}}]}}'

Expected output

pod/web patched

Step 4: Inspect resize status and scheduler conditions

Check status.resize on the pod object to verify whether the node accepted the resize or flagged it as blocked. When the node lacks unallocated capacity, the field shows Infeasible or Deferred, meaning the container stays at its old resource limits until space opens up or preemption occurs.

kubectl get pod web -n demo -o jsonpath='{"Resize status: "}{.status.resize}{"\nAllocated CPU: "}{.status.containerStatuses[0].allocatedResources.cpu}{"\n"}'

Expected output

Resize status: Infeasible
Allocated CPU: 250m

Step 5: Check events for preemption warnings

When a resize request with high priority cannot fit on a saturated node, the scheduler evaluates lower priority pods on that node for preemption. Inspect the events in the namespace to see if the control plane rejected the resize or marked neighbouring pods for eviction.

kubectl get events -n demo --field-selector involvedObject.name=web --sort-by='.metadata.creationTimestamp'

Expected output

LAST SEEN   TYPE      REASON             OBJECT        MESSAGE
42s         Normal    PodResizePending   pod/web       Node worker-1 has insufficient cpu to accommodate the resize
15s         Warning   ResizeInfeasible   pod/web       Resize request cannot be accommodated by node and is marked Infeasible

Why this matters

The in-place pod resize feature solves one of the oldest Kubernetes operational pain points: changing CPU and memory boundaries without restarting containers. However, a pod cannot simply expand beyond the remaining unallocated physical capacity of its assigned node. If a node is fully packed, the pod enters an Infeasible or Deferred state, leaving your workload throttled despite the successful patch command.

When combined with PriorityClass definitions, an in-place resize can trigger the node scheduler to free up capacity by terminating lower-priority pods running alongside your application. Those preempted pods do not pause or migrate; they are permanently killed and must be recreated elsewhere by their respective controllers. If you do not monitor status.resize and node headroom, an emergency resize intended to save a critical app can quietly take down background queues, logging sidecars, or companion services.

Common mistakes

  • Assuming kubectl patch pod guarantees the container received more resources immediately. The patch updates spec.containers[*].resources, but the container only gets the new limits once status.allocatedResources updates. Fix: always inspect .status.resize and verify the value has returned to empty after patch execution.
  • Omitting resizePolicy in pod manifests. Without setting restartPolicy: NotRequired for CPU and memory, the kubelet will default to restarting the container during the resize. Fix: explicitly declare resizePolicy for each resource key in the container specification.
  • Resizing memory on nodes with low swap and no spare RAM. If an in-place memory increase cannot be fulfilled immediately, the kubelet will refuse it to prevent out-of-memory kernel panics. Fix: ensure your node allocatable memory has sufficient headroom before submitting memory resize patches.
  • Setting high priority on unmanaged standalone pods. If a standalone pod gets preempted to make room for a resized pod, nothing recreates it. Fix: ensure all workloads running beside high-priority apps are backed by ReplicaSet or StatefulSet controllers.

Quick recap

  1. Define a clear PriorityClass so the scheduler understands resource importance across workloads.
  2. Configure resizePolicy with restartPolicy: NotRequired to allow seamless dynamic allocation.
  3. Patch spec.containers[*].resources on the live pod to submit the resize request.
  4. Inspect status.resize to ensure the node accepted the change rather than marking it Infeasible.
  5. Review namespace events to verify whether node saturation triggered eviction of neighbouring pods.
