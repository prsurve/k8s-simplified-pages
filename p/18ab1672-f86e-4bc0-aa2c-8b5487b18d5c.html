FIVE TOOLS

By the end of this guide, you will be able to deploy, inspect, debug, and troubleshoot workloads in Kubernetes using only five core kubectl commands. Memorizing hundreds of CLI flags is a trap that slows beginners down; real engineers rely on a tight diagnostic loop to isolate issues quickly. Master these five commands first, and you will handle 90% of your day-to-day Kubernetes tasks with confidence.

Why this matters

The official Kubernetes documentation lists dozens of subcommands and hundreds of flags, making the tool feel overwhelming. In production, however, your job usually boils down to a simple cycle: deploy a manifest, check if the pods are running, read the system events if they fail, inspect the application logs, and open a terminal inside the container if you need to test network access. Committing this five-command loop to muscle memory frees your mental bandwidth so you can focus on diagnosing actual architecture and configuration problems instead of hunting for syntax.

Step 1: Deploy your workload with kubectl apply

Use kubectl apply to submit your desired configuration to the Kubernetes API server. This command is declarative, meaning it creates resources if they do not exist or updates them in place if they do.

kubectl create namespace demo
kubectl apply -n demo -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - containerPort: 80
EOF

Expected output

namespace/demo created
deployment.apps/web created

Step 2: Check resource status with kubectl get

Run kubectl get to see a quick summary of what exists in your cluster and whether your workloads are healthy. Adding the -o wide flag gives you essential network details like pod IP addresses and the assigned worker nodes.

kubectl get pods -n demo -o wide

Step 3: Inspect cluster events with kubectl describe

When a pod fails to start, use kubectl describe to inspect its lifecycle events and detailed specifications. This command tells you what the Kubernetes control plane is doing, exposing common issues like scheduling failures, pull errors, or failed health probes.

kubectl describe pod web-7cbdcb4756-8w2lz -n demo

Step 4: Stream application output with kubectl logs

Once your container is running, use kubectl logs to read the application's stdout and stderr streams. Adding the -f flag streams new log entries directly to your terminal in real time, which is critical for verifying traffic handling and application errors.

kubectl logs web-7cbdcb4756-8w2lz -n demo -f

Step 5: Troubleshoot from the inside with kubectl exec

Use kubectl exec to run commands or open an interactive shell inside a running container. The flags -i (interactive) and -t (tty) let you access the environment directly to test internal DNS resolution, query local endpoints, or verify mounted config files.

kubectl exec -it web-7cbdcb4756-8w2lz -n demo -- curl -I http://localhost:80

Common mistakes

  • Missing the namespace flag: Running kubectl get pods displays No resources found in default namespace. Fix this by passing -n demo explicitly, or set a default namespace for your current context using kubectl config set-context --current --namespace=demo.
  • Confusing cluster issues with app issues: Running kubectl logs when a pod is stuck in ImagePullBackOff results in Error from server (BadRequest): container "nginx" in pod "web-..." is not waiting to start: PodInitializing. Fix this by running kubectl describe first to check cluster events before checking application logs.
  • Running commands in multi-container pods without container targeting: Using kubectl logs or kubectl exec on pods with multiple containers produces error: a container name must be specified for pod web-.... Fix this by specifying the target container with the -c nginx flag.
  • Misunderstanding container shell availability: Running kubectl exec -it <pod> -- /bin/bash fails with executable file not found in $PATH on minimal or distroless images. Fix this by targeting /bin/sh instead, or run single self-contained binaries like curl or cat directly without spawning a shell.

Quick recap

  1. Apply desired state to the cluster using kubectl apply -f manifest.yaml.
  2. Inspect pod health and status summaries using kubectl get pods -o wide.
  3. Investigate deployment bottlenecks and platform events using kubectl describe pod.
  4. Monitor application output and runtime errors using kubectl logs -f.
  5. Enter the runtime environment for deep network and filesystem debugging using kubectl exec -it.
